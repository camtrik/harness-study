# 阶段上下文模板

`.planning/phases/XX-name/{phase_num}-CONTEXT.md` 的模板——记录一个阶段的实现决策。

**目的：** 记录下游 agent 需要的决策。研究者用它知道该研究什么。规划器用它知道哪些选择已锁定 vs 可灵活调整。

**核心原则：** 分类不是预定义的。它们是针对此阶段实际讨论的内容自然涌现的。CLI 阶段有 CLI 相关的段，UI 阶段有 UI 相关的段。

**下游消费者：**
- `gsd-phase-researcher` — 阅读决策以聚焦研究（例如"卡片布局" → 研究卡片组件模式）
- `gsd-planner` — 阅读决策以创建具体任务（例如"无限滚动" → 任务包含虚拟化）

---

**示例 1：视觉功能（帖子信息流）**

```markdown
# 阶段 3：帖子信息流 - 上下文

**收集日期：** 2025-01-20
**状态：** 可规划

<domain>
## 阶段边界

在可滚动信息流中显示已关注用户的帖子。用户可以查看帖子和互动计数。创建帖子和互动是独立的阶段。

</domain>

<decisions>
## 实现决策

### 布局风格
- 基于卡片的布局，非时间线或列表
- 每张卡片显示：作者头像、姓名、时间戳、帖子全文、反应计数
- 卡片有微妙阴影、圆角——现代感

### 加载行为
- 无限滚动，非分页
- 移动端支持下拉刷新
- 顶部显示新帖子指示器（"3 条新帖子"）而非自动插入

### 空状态
- 友好的插图 + "关注他人以查看帖子"
- 基于兴趣推荐 3-5 个账号

### Claude 的自由裁量权
- 加载骨架屏设计
- 精确间距和排版
- 错误状态处理

</decisions>

<canonical_refs>
## 规范参考

### 信息流展示
- `docs/features/social-feed.md` — 信息流需求、帖子卡片字段、互动显示规则
- `docs/decisions/adr-012-infinite-scroll.md` — 滚动策略决策、虚拟化需求

### 空状态
- `docs/design/empty-states.md` — 空状态模式、插图指南

</canonical_refs>

<specifics>
## 具体想法

- "我喜欢 Twitter 在不干扰你滚动位置的情况下显示新帖子指示器的方式"
- 卡片应该像 Linear 的 issue 卡片——简洁，不杂乱

</specifics>

<deferred>
## 延迟的想法

- 评论帖子 — 阶段 5
- 收藏帖子 — 添加到 backlog

</deferred>

---

*阶段：03-post-feed*
*上下文收集日期：2025-01-20*
```

**示例 2：CLI 工具（数据库备份）**

```markdown
# 阶段 2：备份命令 - 上下文

**收集日期：** 2025-01-20
**状态：** 可规划

<domain>
## 阶段边界

将数据库备份到本地文件或 S3 的 CLI 命令。支持完整和增量备份。恢复命令是独立的阶段。

</domain>

<decisions>
## 实现决策

### 输出格式
- 程序化使用用 JSON，人工阅读用表格格式
- 默认表格，--json 标志输出 JSON
- Verbose mode (-v) 显示进度，默认静默

### 标志设计
- 常用选项的短标志：-o（output）、-v（verbose）、-f（force）
- 长标志用于清晰性：--incremental、--compress、--encrypt
- 必需：数据库连接字符串（位置参数或 --db）

### 错误恢复
- 网络失败时重试 3 次，然后失败并给出清晰消息
- --no-retry 标志用于快速失败
- 失败时删除部分备份（无损坏文件）

### Claude 的自由裁量权
- 精确的进度条实现
- 压缩算法选择
- 临时文件处理

</decisions>

<canonical_refs>
## 规范参考

### 备份 CLI
- `docs/features/backup-restore.md` — 备份需求、支持的后端、加密规范
- `docs/decisions/adr-007-cli-conventions.md` — 标志命名、退出码、输出格式标准

</canonical_refs>

<specifics>
## 具体想法

- "我想让它感觉像 pg_dump——对数据库人来说很熟悉"
- 应该在 CI 流水线中可用（退出码、无交互式提示）

</specifics>

<deferred>
## 延迟的想法

- 定时备份 — 独立阶段
- 备份轮换/保留 — 添加到 backlog

</deferred>

---

*阶段：02-backup-command*
*上下文收集日期：2025-01-20*
```

**示例 3：组织任务（照片库）**

```markdown
# 阶段 1：照片组织 - 上下文

**收集日期：** 2025-01-20
**状态：** 可规划

<domain>
## 阶段边界

将现有照片库组织为结构化文件夹。处理重复项并应用一致的命名。标记和搜索是独立的阶段。

</domain>

<decisions>
## 实现决策

### 分组标准
- 主分组按年，然后按月
- 通过时间聚类检测事件（2 小时内的照片 = 同一事件）
- 事件文件夹命名使用日期 + 位置（如可用）

### 重复处理
- 保留最高分辨率版本
- 将重复项移至 _duplicates 文件夹（不删除）
- 记录所有重复决策以供审查

### 命名约定
- 格式：YYYY-MM-DD_HH-MM-SS_originalname.ext
- 保留原始文件名作为后缀以支持搜索
- 使用递增后缀处理名称冲突

### Claude 的自由裁量权
- 精确的聚类算法
- 如何处理没有 EXIF 数据的照片
- 文件夹 emoji 使用

</decisions>

<canonical_refs>
## 规范参考

### 组织规则
- `docs/features/photo-organization.md` — 分组规则、重复策略、命名规范
- `docs/decisions/adr-003-exif-handling.md` — EXIF 提取策略、缺失元数据的回退方案

</canonical_refs>

<specifics>
## 具体想法

- "我想能够按大约拍摄时间找到照片"
- 不要删除任何东西——最坏情况，移至审查文件夹

</specifics>

<deferred>
## 延迟的想法

- 人脸检测分组 — 未来阶段
- 云同步 — 当前超出范围

</deferred>

---

*阶段：01-photo-organization*
*上下文收集日期：2025-01-20*
```

</good_examples>

<guidelines>
**此模板为下游 agent 记录决策。**

输出应回答："研究者需要调查什么？规划器有哪些选择是已锁定的？"

**好的内容（具体决策）：**
- "基于卡片的布局，非时间线"
- "网络失败时重试 3 次，然后失败"
- "按年分组，然后按月"
- "程序化使用用 JSON，人工使用用表格"

**不好的内容（过于模糊）：**
- "应该感觉现代且干净"
- "良好的用户体验"
- "快速且响应及时"
- "易于使用"

**创建之后：**
- 文件位于阶段目录：`.planning/phases/XX-name/{phase_num}-CONTEXT.md`
- `gsd-phase-researcher` 使用决策聚焦调查，并阅读 canonical_refs 了解该研究哪些文档
- `gsd-planner` 使用决策 + 研究创建可执行任务，并阅读 canonical_refs 验证对齐
- 下游 agent 不应该需要就已记录的决策再次询问用户

**关键——规范参考：**
- `<canonical_refs>` 段是强制的。每个 CONTEXT.md 必须有一个。
- 如果项目有外部规范、ADR 或设计文档，用完整相对路径列出它们并按主题分组
- 如果 ROADMAP.md 按阶段列出了 `Canonical refs:`，提取并扩展它们
- 散落在决策中的内联提及如 "see ADR-019" 对下游 agent 无用——他们需要在专门可找到的段中看到完整路径和章节引用
- 如果没有外部规范，明确说明——不要默默省略该段
</guidelines>
