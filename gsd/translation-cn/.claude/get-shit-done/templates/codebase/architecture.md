# 架构模板

`.planning/codebase/ARCHITECTURE.md` 的模板——记录概念层面的代码组织结构。

**目的：** 记录代码在概念层面是如何组织的。与 STRUCTURE.md（展示物理文件位置）互补。

<good_examples>
```markdown
# 架构

**分析日期：** 2025-01-20

## 模式概览

**总体：** 带插件系统的 CLI 应用

**关键特征：**
- 带子命令的单可执行文件
- 基于插件的可扩展性
- 基于文件的状态（无数据库）
- 同步执行模型

## 层次

**命令层：**
- 用途：解析用户输入并路由到适当的处理函数
- 包含：命令定义、参数解析、帮助文本
- 位置：`src/commands/*.ts`
- 依赖于：服务层执行业务逻辑
- 被以下使用：CLI 入口点（`src/index.ts`）

**服务层：**
- 用途：核心业务逻辑
- 包含：FileService、TemplateService、InstallService
- 位置：`src/services/*.ts`
- 依赖于：文件系统工具、外部工具
- 被以下使用：命令处理函数

**工具层：**
- 用途：共享辅助函数和抽象
- 包含：文件 I/O 包装器、路径解析、字符串格式化
- 位置：`src/utils/*.ts`
- 依赖于：仅 Node.js 内置模块
- 被以下使用：服务层

## 数据流

**CLI 命令执行：**

1. 用户运行：`gsd new-project`
2. Commander 解析参数和标志
3. 调用命令处理函数（`src/commands/new-project.ts`）
4. 处理函数调用服务方法（`src/services/project.ts` → `create()`）
5. 服务读取模板、处理文件、写入输出
6. 结果输出到控制台
7. 进程以状态码退出

**状态管理：**
- 基于文件：所有状态位于 `.planning/` 目录中
- 无持久的内存状态
- 每次命令执行是独立的

## 关键抽象

**Service：**
- 用途：封装某个领域的业务逻辑
- 示例：`src/services/file.ts`、`src/services/template.ts`、`src/services/project.ts`
- 模式：类单例（作为模块导入，不实例化）

**Command：**
- 用途：CLI 命令定义
- 示例：`src/commands/new-project.ts`、`src/commands/plan-phase.ts`
- 模式：Commander.js 命令注册

**Template：**
- 用途：可重用的文档结构
- 示例：PROJECT.md、PLAN.md 模板
- 模式：带替换变量的 Markdown 文件

## 入口点

**CLI 入口：**
- 位置：`src/index.ts`
- 触发：用户运行 `gsd <command>`
- 职责：注册命令、解析参数、显示帮助

**命令：**
- 位置：`src/commands/*.ts`
- 触发：CLI 匹配的命令
- 职责：验证输入、调用服务、格式化输出

## 错误处理

**策略：** 抛出异常，在命令层捕获，记录并退出

**模式：**
- 服务抛出带描述性消息的 Error
- 命令处理函数捕获、记录错误到 stderr、exit(1)
- 在执行前显示验证错误（快速失败）

## 横切关注点

**日志：**
- console.log 用于常规输出
- console.error 用于错误
- Chalk 用于彩色输出

**验证：**
- Zod 模式用于配置文件解析
- 命令处理函数中的手动验证
- 无效输入时快速失败

**文件操作：**
- 对 fs-extra 的 FileService 抽象
- 操作前验证所有路径
- 原子写入（临时文件 + 重命名）

---

*架构分析：2025-01-20*
*当主要模式发生变化时更新*
```

<guidelines>
**ARCHITECTURE.md 应包含的内容：**
- 整体架构模式（单体、微服务、分层等）
- 概念层面的层次及其关系
- 数据流 / 请求生命周期
- 关键抽象和模式
- 入口点
- 错误处理策略
- 横切关注点（日志、认证、验证）

**不应包含的内容：**
- 详尽的文件列表（那是 STRUCTURE.md 的事）
- 技术选择（那是 STACK.md 的事）
- 逐行代码走查（推迟到代码阅读时进行）
- 特定功能的实现细节

**欢迎包含文件路径：**
将文件路径作为抽象的具体示例包含进来。使用反引号格式：`src/services/user.ts`。这使架构文档在规划时对 Claude 是可执行的。

**填充此模板时：**
- 阅读主要入口点（index、server、main）
- 通过阅读 import/依赖关系识别层次
- 追踪典型的请求/命令执行
- 注意反复出现的模式（services、controllers、repositories）
- 保持描述是概念层面的，不是机械的

**在以下场景中对阶段规划有用：**
- 添加新功能（它适合放在哪个层次？）
- 重构（理解当前模式）
- 确定在哪里添加代码（哪个层次处理 X？）
- 理解组件之间的依赖关系
</guidelines>
