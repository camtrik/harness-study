# 阶段规范模板

`.planning/phases/XX-name/{phase_num}-SPEC.md` 的模板——在 discuss-phase 之前锁定需求。

**目的：** 记录阶段交付什么以及为什么，精确到需求是可证伪的。discuss-phase 读取此文件并聚焦于如何实现（跳过已在此处回答的"什么/为什么"问题）。

**核心原则：** 每个需求必须是可证伪的——你可以编写一个测试或检查来证明它是否被满足。像"提升性能"这样的模糊需求是不允许的。

**下游消费者：**
- `discuss-phase` — 在启动时读取 SPEC.md；将需求、边界和验收标准视为已锁定；跳过"什么/为什么"问题
- `gsd-planner` — 读取已锁定的需求以约束计划范围
- `gsd-verifier` — 使用验收标准作为明确的通过/不通过检查

---

## 文件模板

```markdown
# 阶段 [X]：[名称] — 规范

**创建日期：** [日期]
**模糊度评分：** [分数]（阈值：≤ 0.20）
**需求：** [N] 个已锁定

## 目标

[一句精确的话——具体且可测量。不是"改进 X"——而是"X 从 A 变为 B"。]

## 背景

[来自代码库的当前状态——今天存在什么、什么坏了或缺失、什么触发了此项工作。基于代码现实，而非抽象描述。]

## 需求

1. **[简短标签]**：[具体、可测试的陈述。]
   - 当前：[今天存在或不存在什么]
   - 目标：[此阶段之后应变成什么]
   - 验收：[具体的通过/不通过检查——验证者如何确认此需求已满足]

2. **[简短标签]**：[具体、可测试的陈述。]
   - 当前：[今天存在或不存在什么]
   - 目标：[此阶段之后应变成什么]
   - 验收：[具体的通过/不通过检查]

[继续列出所有需求。每个需求必须有当前/目标/验收。]

## 边界

**范围内：**
- [此阶段产出物的明确列表]
- [每项都是具体的交付物或行为]

**范围外：**
- [此阶段不做的明确列表] — [简要说明为什么排除]
- [从此阶段排除的邻近问题] — [简要说明]

## 约束

[性能、兼容性、数据量、依赖或平台约束。
如果没有："除了标准项目约定外没有额外约束。"]

## 验收标准

- [ ] [通过/不通过标准——明确、可验证]
- [ ] [通过/不通过标准]
- [ ] [通过/不通过标准]

[每个验收标准必须是一个能解析为 PASS 或 FAIL 的复选框。
不要写"应该感觉不错"、"看起来合理"或"大致可用"——这些不是复选框。]

|--------------------|-------|------|--------|------------------------------------|

| 边界清晰度 | | 0.70 | | |
| 约束清晰度 | | 0.65 | | |

状态：✓ = 达到最低标准，⚠ = 未达最低（规划器视为假设）

## 访谈日志

[苏格拉底式访谈中做出的关键决策。格式：轮次 → 问题 → 回答 → 已锁定决策。]

| 轮次 | 视角 | 问题摘要 | 已锁定决策 |
|-------|----------------|-------------------------|------------------------------------|
| 1 | 研究者 | [问了什么] | [决定了什么] |

*阶段：[XX-name]*
```

<good_examples>

**示例 1：功能添加（帖子信息流）**

```markdown
# 阶段 3：帖子信息流 — 规范

**创建日期：** 2025-01-20
**模糊度评分：** 0.12
**需求：** 4 个已锁定

## 目标

用户可以滚动浏览已关注账号的帖子，下拉刷新后可以看到新帖子。

## 背景

数据库中有 `posts` 表和 `follows` 表。目前不存在信息流查询或信息流 UI。首页显示占位文本"您关注的信息流将在此处显示。"此阶段构建信息流查询、API 端点和信息流列表组件。

## 需求

1. **信息流查询**：返回已关注账号的帖子，按创建时间降序排列。
   - 当前：无信息流查询存在——`posts` 表仅从个人资料页面直接查询
   - 目标：`GET /api/feed` 返回已关注账号的分页帖子，最新排前，每页最多 20 条
   - 验收：查询为关注 3 个账号且已知帖子数量的用户返回正确的帖子；基于游标的分页正确前进

2. **信息流展示**：帖子在可滚动的卡片列表中显示。
   - 当前：首页显示静态占位文本
   - 目标：首页渲染信息流卡片，含作者、时间戳、帖子内容和回应计数
   - 验收：信息流在 0 条帖子（显示空状态）、1 条帖子和 20+ 条帖子时均正常渲染

3. **下拉刷新**：用户可以手动刷新信息流。
   - 当前：无刷新机制
   - 目标：下拉手势触发重新获取；新帖子出现在列表顶部
   - 验收：在测试中创建新帖子后，下拉刷新显示新帖子，无需完全重启应用

4. **新帖子指示器**：新帖子到达时显示横幅而非自动滚动。
   - 当前：无此机制
   - 目标：当重新获取返回的帖子比最旧可见帖更新时显示"3 条新帖子"横幅；点击横幅滚动到顶部并显示新帖子
   - 验收：≥1 条新帖子时横幅出现，无新帖时不出现，点击导航到顶部

## 边界

**范围内：**
- 信息流查询（后端）——来自已关注账号的帖子，分页
- 信息流列表 UI（前端）——含作者、时间戳、内容、回应计数的帖子卡片
- 下拉刷新手势
- 新帖子指示器横幅
- 用户未关注任何人或无帖子时的空状态

**范围外：**
- 创建帖子 — 那是阶段 4
- 回应帖子 — 那是阶段 5
- 关注/取消关注 — 那是阶段 2（已完成）
- 新帖子的推送通知 — 单独的 backlog 项

## 约束

- 信息流查询必须使用基于游标的分页（非偏移）——数据库有 500K+ 帖子，偏移分页在第 3 页之后慢得不可接受
- 信息流卡片组件必须复用阶段 2 中的现有 `<AvatarImage>` 组件

## 验收标准

- [ ] `GET /api/feed` 仅返回已关注账号的帖子（非全部帖子）
- [ ] `GET /api/feed` 支持 `cursor` 参数进行分页
- [ ] 信息流在 0、1 和 20+ 条帖子时均正确渲染
- [ ] 下拉刷新触发重新获取
- [ ] 存在比当前视图更新的帖子时显示新帖子指示器
- [ ] 用户未关注任何人时空状态渲染正确

## 模糊度报告

| 维度 | 评分 | 最低 | 状态 | 备注 |
|--------------------|-------|------|--------|----------------------------------|
| 目标清晰度 | 0.92 | 0.75 | ✓ | |
| 边界清晰度 | 0.95 | 0.70 | ✓ | 明确的范围外列表 |
| 约束清晰度 | 0.80 | 0.65 | ✓ | 需要游标分页 |
| 验收标准 | 0.85 | 0.70 | ✓ | 6 个通过/不通过标准 |
| **模糊度** | 0.12 | ≤0.20| ✓ | |
```

<guidelines>
**每个需求需要全部三个字段：**
- 当前：将需求锚定在现实中——今天存在什么？
- 目标：具体的变化——不是"改进 X"而是"X 变为 Y"
- 验收：可证伪的检查——验证者如何确认这一点？

**模糊度报告必须反映真实的访谈。** 如果某个维度低于最低标准，标记 ⚠——规划器知道将其视为假设而非锁定的需求。

**访谈日志是严谨性的证据。** 不要跳过它。它显示需求来自发现而非假设。

**边界保护阶段免受范围蔓延。** 范围外列表及其理由与范围内列表同样重要。触及邻近领域的未来阶段可以引用此 SPEC.md 来了解什么被有意排除了。

**SPEC.md 是需求的单向门。** discuss-phase 将这些视为已锁定。如果 SPEC.md 写完后需求发生变化，用户应首先更新 SPEC.md，然后重新运行 discuss-phase。

**SPEC.md 不替代 CONTEXT.md。** 它们服务不同的目的：
- SPEC.md：阶段交付什么（需求、边界、验收标准）
- CONTEXT.md：阶段如何实现（决策、模式、权衡）

discuss-phase 在阅读 SPEC.md 后生成 CONTEXT.md。
</guidelines>
