# PROJECT.md 模板

`.planning/PROJECT.md` 的模板——动态的项目上下文文档。

<template>

```markdown
# [项目名称]

## 这是什么

[当前的准确描述——2-3 句话。这个产品做什么，面向谁？
使用用户的语言和表述方式。当实际情况与此描述偏离时更新。]

## 核心价值

[最重要的一件事。如果其他一切都失败了，这个必须正常工作。
一句在出现权衡时驱动优先级排序的话。]

## 需求

### 已验证的需求

<!-- 已发布并确认有价值的。 -->

（尚未——发布以验证）

### 活跃的需求

<!-- 当前的范围。正在朝这些目标建设。 -->

- [ ] [需求 1]
- [ ] [需求 2]
- [ ] [需求 3]

### 排除的范围

<!-- 明确的边界。包含推理以防止后续重新添加。 -->

- [排除项 1] — [为什么]
- [排除项 2] — [为什么]

## 上下文

[为实现提供信息的背景信息：
- 技术环境或生态系统
- 相关的先前工作或经验
- 用户研究或反馈主题
- 需要解决的已知问题]

## 约束

- **[类型]**：[什么] — [为什么]
- **[类型]**：[什么] — [为什么]

常见类型：技术栈、时间线、预算、依赖、兼容性、性能、安全

## 关键决策

<!-- 约束未来工作的决策。在项目生命周期中添加。 -->

| 决策 | 理由 | 结果 |
|----------|-----------|---------|
| [选择] | [原因] | [✓ 良好 / ⚠️ 重新评估 / — 待定] |

---
*最后更新：[日期]，更新原因：[触发事件]*
```

</template>

<guidelines>

**这是什么：**
- 当前产品的准确描述
- 2-3 句话说明它做什么以及面向谁
- 使用用户的语言和表述方式
- 当产品已超出此描述时更新

**核心价值：**
- 唯一最重要的事
- 其他一切都可以失败；这个不能
- 在出现权衡时驱动优先级排序
- 很少改变；如果改变了，说明是一次重大 pivot

**需求——已验证：**
- 已发布并证明有价值的需求
- 格式：`- ✓ [需求] — [版本/阶段]`
- 这些是锁定的——变更它们需要明确讨论

**需求——活跃：**
- 正在建设中的当前范围
- 这些是假设，直到发布和验证
- 发布后移至已验证，失效则移至排除范围

**需求——排除范围：**
- 关于我们不构建什么的明确边界
- 始终包含推理（防止后续重新添加）
- 包含：已考虑并拒绝的、延迟到未来的、明确排除的

**上下文：**
- 为实现决策提供信息的背景
- 技术环境、先前工作、用户反馈
- 需要解决的已知问题或技术债务
- 新上下文出现时更新

**约束：**
- 对实现选择的硬性限制
- 技术栈、时间线、预算、兼容性、依赖
- 包含"为什么"——没有理由的约束会被质疑

**关键决策：**
- 影响未来工作的重大选择
- 在整个项目过程中随决策做出而添加
- 当结果已知时跟踪：
  - ✓ 良好 — 决策被证明正确
  - ⚠️ 重新评估 — 决策可能需要重新考虑
  - — 待定 — 评估尚早

**最后更新：**
- 始终注明文档何时更新及原因
- 格式：`阶段 2 之后` 或 `v1.0 里程碑之后`
- 触发对内容是否仍然准确的审查

</guidelines>

<evolution>

PROJECT.md 在项目生命周期中演化。
这些规则嵌入在生成的 PROJECT.md 中（## Evolution 段），由 workflows/transition.md 和 workflows/complete-milestone.md 执行。

**每个阶段转换之后：**
1. 需求被否定？→ 移至排除范围，附原因
2. 需求已验证？→ 移至已验证，附阶段引用
3. 新需求出现？→ 添加到活跃
4. 有决策要记录？→ 添加到关键决策
5. "这是什么"仍然准确？→ 如有偏离则更新

**每个里程碑之后：**
1. 对所有段进行全面审查
2. 核心价值检查——仍然是最正确的优先级吗？
3. 审计排除范围——理由仍然有效吗？
4. 用当前状态更新上下文（用户、反馈、指标）

</evolution>

<brownfield>

对于已有代码库：

1. **首先映射代码库** 通过 `/gsd-map-codebase`

2. **从现有代码推断已验证的需求**：
   - 代码库实际做什么？
   - 已建立了什么模式？
   - 什么明显在工作并被依赖？

3. **从用户那里收集活跃的需求**：
   - 呈现推断出的当前状态
   - 询问他们接下来想构建什么

4. **初始化：**
   - 已验证 = 从现有代码推断
   - 活跃 = 用户对本次工作的目标
   - 排除范围 = 用户指定的边界
   - 上下文 = 包含当前代码库状态

</brownfield>

<state_reference>

STATE.md 引用 PROJECT.md：

```markdown
## Project Reference

参见：.planning/PROJECT.md（更新于 [日期]）

**核心价值：** [来自核心价值段的一句话]
**当前焦点：** [当前阶段名称]
```

这确保 Claude 读取当前的 PROJECT.md 上下文。

</state_reference>
