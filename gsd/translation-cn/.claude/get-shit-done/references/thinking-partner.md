# 思考伙伴集成

在工作流决策点的条件式扩展思考。当 `.planning/config.json` 中 `features.thinking_partner: true` 时激活（默认：false）。

---

## 权衡检测信号

当开发者的响应包含表明竞争优先级的特定信号时，思考伙伴激活：

**关键词信号：**
- 连接两种方法的"or" / "versus" / "vs"
- "tradeoff" / "trade-off" / "tradeoffs"
- "on one hand" / "on the other hand"
- "pros and cons"
- "not sure between" / "torn between"

**结构信号：**
- 开发者列出 2+ 个竞争选项
- 开发者问"which is better"或"what would you recommend"
- 开发者撤销先前的决策（"actually, maybe we should..."）

**何时不激活：**
- 开发者已经做出明确选择
- "or"是修辞性或琐碎的（例如"tabs or spaces"——使用项目惯例）
- 简单的是/否问题
- 开发者明确要求继续前进

---

## 集成点

### 1. 讨论阶段——权衡深入

**时机：** 在 `discuss_areas` 步骤中，开发者回答揭示竞争优先级后。

**内容：** 暂停正常问题流并提供简短的架构分析：
```
我注意到这里有竞争优先级——{X} 优化 {A} 而 {Y} 优化 {B}。

要我在决定前思考权衡吗？
[是，分析权衡] / [否，我已决定]
```

如果是，提供一个简短（3-5 个要点）的分析，涵盖：
- 每种方法优化什么
- 每种方法牺牲什么
- 哪种更符合项目所述目标（来自 PROJECT.md）
- 带有推理的推荐

然后返回正常讨论流程。

### 2. 计划阶段——架构决策分析

**时机：** 在步骤 11（处理检查器返回）中，plan-checker 标记包含架构权衡关键词的问题时。

**内容：** 在发送到修订循环之前，分析架构决策：
```
plan-checker 标记了一个架构权衡：{问题描述}

简要分析：
- 选项 A：{方法}——{优缺点}
- 选项 B：{方法}——{优缺点}
- 推荐：{选择}，因为 {与阶段目标对齐的推理}

将此推荐应用到修订中？[是] / [否，让我决定]
```

### 3. 探索——方法比较（需要 #1729）

**时机：** 在苏格拉底对话中，当出现多个可行方法时。
**注意：** 此集成点将在 /gsd-explore（#1729）落地时添加。

## 配置

```json
{
  "features": {
    "thinking_partner": true
  }
}
```

默认：`false`。思考伙伴是选择性加入的，因为它为交互工作流增加了延迟。

---

## 设计原则

1. **轻量**——行内分析，而非单独的交互会话
2. **选择性加入**——必须显式启用，从不默认激活
3. **可跳过**——始终提供"否，我已决定"以绕过
4. **简短**——最多 3-5 个要点，不是完整研究报告
5. **对齐**——推荐在可用时引用 PROJECT.md 目标
