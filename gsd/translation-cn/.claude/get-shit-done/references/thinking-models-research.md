# 思维模型：研究集群

用于 **researcher** 和 **synthesizer** agent 的结构化推理模型。在研究和综合中的决策点应用它们，而非持续应用。每个模型针对一个特定的已记录的失败模式。

来源：精选自 [thinking-partner](https://github.com/mattnowdev/thinking-partner) 模型目录（150+ 模型）。选择是因为直接适用于 GSD 研究工作流。

## 冲突解决

**第一性原则和钢铁人都在扩展范围**——先运行第一性原则（分解问题），再运行钢铁人（强化替代方案）。不要同时运行。

## 1. 第一性原则思考

**针对：** 接受表面解释而不分解为基本组件。

在接受任何技术推荐或架构模式之前，将其分解为基本约束：这解决什么问题？不可协商的需求是什么？物理/逻辑限制是什么？从这些约束向上构建你的推荐，而不是从常规智慧向下。如果你不能从第一性原则解释为什么推荐是正确的，无论来源数量如何，将其标记为 `[LOW]`。

## 2. 辛普森悖论意识

**针对：** Synthesizer 在不检查混杂分裂的情况下聚合冲突研究。

当组合显示矛盾结果的多个研究文档发现时，检查当你按隐藏变量拆分时矛盾是否消失：框架版本、部署目标、项目规模或用例类别。一个在总体上基准更快的库可能对你特定的工作负载更慢。在以多数投票解决矛盾之前，问："是否存在一个子群分裂能解释为什么两个发现在其各自上下文中都是正确的？"

## 3. 幸存者偏差

**针对：** 只找到成功示例而遗漏失败和废弃方法。

在收集支持推荐方法的证据之后，主动搜索废弃了它的项目。检查 GitHub issues 的"migrated away from"、"replaced X with"或"problems with X at scale"。一个拥有 10 个成功故事和 100 个安静失败的技术看起来很好，直到你检查墓地。对负面证据（迁移离开故事、废弃通知、未解决的问题）赋予比正面证据更高的权重——失败被低报告。

## 4. 确认偏差对抗

**针对：** 搜索确认初始假设的证据而忽略反驳证据。

在形成初始推荐后，花一个完整研究周期搜索反对它。使用搜索词如"{technology} problems"、"{technology} alternatives"、"why not {technology}"、"{technology} vs {competitor}"。对发现的每个反驳证据，要么（a）用更高信心的来源反驳它，要么（b）将其作为警示添加到你的推荐中。如果你找不到对你推荐的任何批评，你的搜索太窄——加宽它。

## 5. 钢铁人

**针对：** 在不给予替代方案最强形式的情况下驳回它们。

在推荐反对替代技术或方法之前，构建其最强的可能案例。一个热情的倡议者会说什么？什么用例它比你的推荐更好地服务？什么权衡对它有利？将钢铁人替代方案与你的推荐并排呈现，附上诚实的比较。如果钢铁人替代方案有竞争力，将决策标记为 `[NEEDS DECISION]` 而非做出单方面推荐。

---

## 何时不思考

在以下情况下跳过结构化推理模型：

- **CONTEXT.md 中的锁定决策**——如果用户已经决定"使用库 X"，不要对替代方案运行钢铁人分析或选择的第一性原则分解。研究如何良好地使用 X，而非 X 是否是正确的选择。
- **标准技术栈查询**——如果你只是检查知名库的最新版本或阅读其 API 文档，不要调用幸存者偏差或确认偏差对抗。这些模型用于评估有争议的推荐，而非事实性查询。
- **单一技术阶段**——如果阶段涉及一种技术且没有评估替代方案（例如"添加 ESLint 规则 X"），跳过比较模型（钢铁人、确认偏差对抗）。仅研究实现。
- **纯代码库研究**——如果研究是纯内部的（理解现有代码模式、查找函数在哪里被调用），结构化推理模型不增加价值。使用 grep 并阅读代码。
