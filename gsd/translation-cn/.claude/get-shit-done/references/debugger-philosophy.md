# 调试哲学

长期有效的调试原则——适用于每个 bug、每种语言、每个系统。由 `gsd-debugger` 通过 `@file` 引用加载。

## 用户 = 报告者，Claude = 调查者

用户知道：
- 他们预期发生什么
- 实际发生了什么
- 他们看到的错误消息
- 何时开始的 / 是否曾正常工作

用户不知道（不要问）：
- 什么导致了 bug
- 哪个文件有问题
- 修复应该是什么

询问关于体验的问题。自行调查原因。

## 元调试：你自己的代码

在调试自己写的代码时，你是在与自己的思维模型对抗。

**为什么更难：**
- 你做了设计决策——它们感觉明显正确
- 你记得意图，而不是实际实现的内容
- 熟悉导致对 bug 视而不见

**守则：**
1. **把自己的代码当作别人的**——像读别人的代码一样读它
2. **质疑你的设计决策**——你的实现决策是假设，不是事实
3. **承认你的思维模型可能错误**——代码的行为是真相；你的模型是猜测
4. **优先检查你碰过的代码**——如果你修改了 100 行代码且出了 bug，那些是首要嫌疑

**最难承认的：**"我实现错了。"不是"需求不清楚"——是 YOU 犯了一个错误。

## 基本原则

调试时，回到基础事实：

- **你确定知道什么？** 可观察的事实，不是假设
- **你在假设什么？** "这个库应该是这样工作的"——你验证了吗？
- **剥离你认为你知道的一切。** 从可观察的事实出发建立理解。

## 需要避免的认知偏差

| 偏差 | 陷阱 | 解药 |
|------|------|----------|
| **确认** | 只寻找支持你假设的证据 | 主动寻找反驳证据。"什么会证明我是错的？" |
| **锚定** | 第一个解释成为你的锚 | 在调查任何假设之前，生成 3+ 个独立假设 |
| **可得性** | 最近的 bug → 假设类似原因 | 将每个 bug 视作新颖的，直到证据表明并非如此 |
| **沉没成本** | 在一条路上花了 2 小时，尽管证据表明不对仍继续 | 每 30 分钟："如果我从头开始，这还是我会走的路吗？" |

## 系统性调查准则

**一次改变一个变量：** 改变一个东西、测试、观察、记录、重复。多次改变 = 不知道是什么起了作用。

**完整阅读：** 阅读整个函数，而不仅仅是"相关"行。阅读导入、配置、测试。略读会遗漏关键细节。

**拥抱未知：** "我不知道为什么会失败"= 好（现在你可以调查了）。"一定是 X"= 危险（你已经停止思考了）。

## 何时重新开始

考虑从头开始时当：
1. **2+ 小时无进展**——你可能已经进入隧道视野
2. **3+ 个"修复"都不起作用**——你的思维模型是错误的
3. **你无法解释当前行为**——不要在混乱之上叠加更改
4. **你在调试调试器本身**——某些根本性的东西出了错
5. **修复有效但不知道为什么**——这不是修好了，这是运气

**重新开始协议：**
1. 关闭所有文件和终端
2. 写下你确定知道的事实
3. 写下你已经排除的
4. 列出新的假设（与之前不同的）
5. 从阶段 1 重新开始：证据收集
