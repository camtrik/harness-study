# AI 评估参考

> 供 `gsd-eval-planner` 和 `gsd-eval-auditor` 使用的参考文档。
> 基于"AI Evals for Everyone"课程（Reganti & Badam）+ 业界实践。

---

## 核心概念

### 为什么需要评估
AI 系统是非确定性的。输入 X 在不同运行、用户或边界情况下并不能可靠地产生输出 Y。评估是持续评估系统行为是否在真实条件下满足预期的过程——仅有单元测试和集成测试是不够的。

### 模型评估与产品评估
- **模型评估**（MMLU、HumanEval、GSM8K）——在标准化条件下衡量通用能力。仅作为初步筛选。
- **产品评估**——衡量在特定系统中的行为，包括你的数据、用户和领域规则。80% 的评估精力应放在这里。

### 每个评估的三个组成部分
- **输入**——影响系统的所有因素：查询、历史记录、检索文档、system prompt、配置
- **预期**——良好行为的定义，通过评分标准明确
- **实际**——系统产生的输出，包括中间步骤、工具调用和推理轨迹

### 三种衡量方法
1. **基于代码的指标**——确定性检查：JSON 验证、必需的免责声明、性能阈值、分类标记。快速、廉价、可靠。优先使用。
2. **LLM 评判**——由一个模型按评分标准评估另一个模型。对于主观性品质（语气、推理、升级判断）非常有效。在信任之前必须先与人类判断进行校准。
3. **人工评估**——细微判断的黄金标准。无法规模化。用于校准、边界情况、定期采样和高风险决策。

最有效的系统三者结合使用。

## 评估维度

### 部署前（开发阶段）

| 维度 | 衡量什么 | 何时重要 |
|-----------|-----------------|-----------------|
| **事实准确性** | 声明的正确性与事实基准对照 | RAG、知识库、任何事实性断言 |
| **上下文忠实度** | 响应是否基于提供的上下文而非虚构 | RAG 流水线、文档问答、检索增强系统 |
| **幻觉检测** | 看似合理但无根据的声明 | 所有生成系统、高风险领域 |
| **升级准确性** | 正确识别何时需要人工介入 | 客服、医疗、金融咨询 |
| **策略合规性** | 遵守业务规则、法律要求、免责声明 | 受监管行业、企业部署 |
| **语气/风格适当性** | 匹配品牌调性、受众期望、情感上下文 | 面向客户的系统、内容生成 |
| **输出结构有效性** | 模式合规、必需字段、格式正确性 | 结构化提取、API 集成、数据流水线 |
| **任务完成度** | 系统是否完成既定目标 | agentic 工作流、多步骤任务 |
| **工具使用正确性** | 工具的正确选择和调用 | 带工具调用的 agent 系统 |
| **安全性** | 没有有害、偏见或不适当的输出 | 所有面向用户的系统 |

### 生产监控

| 维度 | 监控方法 |
|-----------|---------------------|
| **安全违规** | 在线护栏——实时、即时干预 |
| **合规失败** | 在线护栏——在用户看到输出前阻止或升级 |
| **质量退化趋势** | 离线飞轮——对采样的交互进行批量分析 |
| **新出现的失败模式** | 信号-指标背离——当用户行为信号偏离指标分数时，手动调查 |
| **成本/延迟漂移** | 基于代码的指标——自动化阈值告警 |

## 护栏与飞轮决策

问自己："如果这种行为出错，对我的业务会是灾难性的吗？"

- **是 → 护栏**——在线、实时运行，立即干预（阻止、升级、转交）。需要谨慎选择：护栏会增加延迟。
- **否 → 飞轮**——离线作为批量分析运行，随时间推移反馈系统改进。

## 评分标准设计

脱离上下文的通用指标毫无意义。"有帮助性"在房地产领域意味着清晰地总结房源信息，在医疗领域意味着知道何时*不*回答问题。

评分标准必须定义：
1. 被衡量的维度
2. 5 分制中 1、3、5 分的具体含义（或通过/失败标准）
3. 可接受与不可接受行为的领域特定示例

没有评分标准，LLM 评判产生的是噪音而非信号。

## 参考数据集指南

- 从 **10-20 个高质量示例**开始——而不是 200 个平庸的示例
- 覆盖：关键成功场景、常见用户工作流、已知边界情况、历史失败模式
- 让领域专家标注示例（不仅仅是工程师）
- 根据在生产中学到的经验扩展——不要为了假设性的覆盖率而构建

## 评估工具指南

| 工具 | 类型 | 最适合 | 核心优势 |
|------|------|----------|-------------|
| **RAGAS** | Python 库 | RAG 评估 | 专为 RAG 设计的指标：忠实度、答案相关性、上下文精确度/召回率 |
| **Langfuse** | 平台（开源，可自托管） | 所有系统类型 | 强大的追踪、prompt 管理，适合需要基础设施控制的团队 |
| **LangSmith** | 平台（商业） | LangChain/LangGraph 生态系统 | 与 LangChain 最紧密集成；如果已在该生态中则是最佳选择 |
| **Arize Phoenix** | 平台（开源 + 托管） | RAG + 多 agent 追踪 | 强大的 RAG 评估 + 追踪可视化；开源且提供托管选项 |
| **Braintrust** | 平台（商业） | 模型无关评估 | 数据集和实验管理；适合跨框架比较 |
| **Promptfoo** | CLI 工具（开源） | Prompt 测试、CI/CD | CLI 优先，非常适合 CI/CD prompt 回归测试 |

### 按系统类型选择工具

| 系统类型 | 推荐工具 |
|-------------|---------------------|
| RAG / 知识问答 | RAGAS + Arize Phoenix 或 Braintrust |
| 多 agent 系统 | Langfuse + Arize Phoenix |
| 对话式 / 单模型 | Promptfoo + Braintrust |
| 结构化提取 | Promptfoo + 基于代码的验证器 |
| LangChain/LangGraph 项目 | LangSmith（原生集成） |
| 生产监控（所有类型） | Langfuse、Arize Phoenix 或 LangSmith |

## 开发生命周期中的评估

### 计划阶段（评估感知设计）
在编写代码之前，定义：
1. 正在构建的 AI 系统类型 → 决定框架和主要评估关注点
2. 关键失败模式（3-5 个不能出错的行为）
3. 评分标准——每个维度的可接受/不可接受行为的明确定义
4. 评估策略——哪些维度使用代码指标、LLM 评判或人工审查
5. 参考数据集需求——大小、组成、标注方法
6. 评估工具选择

产出：AI-SPEC.md 的 EVALS-SPEC 节

### 执行阶段（边构建边装备）
- 从第一天就添加追踪（Langfuse、Arize Phoenix 或 LangSmith）
- 与实现同步构建参考数据集
- 先实现基于代码的检查；仅在主观维度上添加 LLM 评判
- 通过 Promptfoo 或 Braintrust 在 CI/CD 中运行评估

### 验证阶段（部署前验证）
- 对所有指标运行完整参考数据集
- 对边界情况和 LLM 评判不一致的情况进行人工审查
- 将 LLM 评判与人工评分进行校准（目标：相关性 ≥ 0.7 后方可信任）
- 定义并配置生产环境护栏
- 建立监控基线

### 监控阶段（生产评估循环）
- 智能采样——优先采样有警示信号的交互（重试、异常长度、显式升级）
- 每次交互都应用在线护栏
- 对采样批次运行离线飞轮
- 关注信号-指标背离——评估盲区的早期预警系统

## 常见陷阱

1. **假设基准测试能预测产品成功**——不能；模型评估是筛选器，不是判决
2. **孤立地进行工程评估**——领域专家必须共同定义评分标准；工程师单独会遗漏关键细微差别
3. **第一天就建立全面覆盖**——从小处着手（10-20 个示例），从真实失败模式中扩展
4. **信任未校准的 LLM 评判**——在依赖之前先与人工判断进行验证
5. **衡量一切**——只追踪能驱动决策的指标；"全收集"产生的是噪音
6. **将评估视为一次性设定**——用户行为会演变，需求会变化，失败模式会涌现；评估是持续的过程
