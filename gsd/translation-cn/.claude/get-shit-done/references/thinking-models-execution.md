# 思维模型：执行集群

用于 **executor** agent 的结构化推理模型。在任务执行中的决策点应用它们，而非持续应用。每个模型针对一个特定的已记录的失败模式。

来源：精选自 [thinking-partner](https://github.com/mattnowdev/thinking-partner) 模型目录（150+ 模型）。选择是因为直接适用于 GSD 执行工作流。

## 冲突解决

**强制函数和第一性原则都推动"现在做"。** 先运行第一性原则（理解约束），再运行强制函数（创建机制）。顺序执行，非竞争。

## 1. 关注圈与掌控圈

**针对：** Executor 尝试修复其范围之外的事情——上游 bug、无关的技术债务、基础设施问题。

在修改计划 `<files>` 部分未明确列出的任何代码之前，问：这是在我的掌控圈（计划范围）还是关注圈（我注意到但不应该修复的事情）？如果是关注圈：将其记录为偏差说明或延迟项，不要修复它。executor 的工作是构建计划所说的内容，而不是改进代码库。"顺便"修复导致的范围蔓延是 executor 超时的头号原因。

## 2. 强制函数

**针对：** 将困难决策推迟到运行时，而非在构建时解决。

当你遇到模糊的需求或不清晰的集成点时，创建一个强制函数，使决策现在明确而非隐藏在 TODO 或运行时检查之后。示例：使用 TypeScript `never` 类型强制穷尽切换，为必需配置值添加构建时断言，创建接口强迫调用方处理错误情况。如果决策确实无法在构建时做出，将其记录为 `checkpoint:decision` 偏差——不要静默延迟。

## 3. 第一性原则思考

**针对：** 从现有代码复制模式而不理解它们是否适合当前任务。

在从其他文件或阶段复制模式之前，分解该模式存在的原因：它满足什么约束？你当前的任务有相同的约束吗？如果没有，该模式可能是货物崇拜。从任务的实际需求构建实现，而非从最近的现有例子。如有疑问，计划的 `<action>` 步骤定义了构建什么——从这些派生实现，而非从相邻代码。

## 4. 奥卡姆剃刀

**针对：** 用不必要的抽象、泛型或未来防护过度设计简单任务。

在添加抽象层、泛型类型参数、工厂模式或配置选项之前，问：计划是否要求这种灵活性？如果计划说"创建一个做 X 的函数"，创建一个做 X 的函数——而不是一个可配置、可扩展、可插拔的框架，理论上可以通过 Y 和 Z 做 X。满足计划 `<done>` 条件的最简实现是正确的。仅在计划明确要求时才添加复杂性。

## 5. 切斯特顿围栏

**针对：** 在不理解为什么代码以某种方式编写的情况下删除或修改现有代码。

在删除、替换或重大修改计划触及的现有代码之前，确定它存在的原因。检查：引入它的 commit 的 git blame、解释理由的注释、测试它的测试用例、创建它的 PLAN.md 或 SUMMARY.md。如果目的不明，保留它并添加一条注释说明不确定性——不要删除你不理解其目的的代码。如果计划明确说要删除它，仍需在偏差说明中记录它做了什么。

---

## 何时不思考

在以下情况下跳过结构化推理模型：

- **直接的任务 action**——如果计划说"创建文件 X 包含内容 Y"且 action 明确，直接执行。不要调用第一性原则分析为什么你要创建计划告诉你创建的文件。
- **遵循既定项目模式**——如果代码库有清晰、一致的模式（例如每个路由处理器遵循相同结构）且计划说要添加另一个，遵循模式。切斯特顿围栏适用于删除模式，而非遵循它们。
- **简单的文件编辑**——添加导入、修复拼写错误、更新版本号。这些是不涉及设计决策的机械更改。
- **运行 verify 命令**——执行计划的 `<verify>` 步骤是过程性的。仅在 verify 步骤失败且需要决定如何响应时才调用模型。
