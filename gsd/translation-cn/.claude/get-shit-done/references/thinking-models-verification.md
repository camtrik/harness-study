# 思维模型：验证集群

用于 **verifier** 和 **plan-checker** agent 的结构化推理模型。在验证过程中应用它们，而非持续应用。每个模型针对一个特定的已记录的失败模式。

来源：精选自 [thinking-partner](https://github.com/mattnowdev/thinking-partner) 模型目录（150+ 模型）。选择是因为直接适用于 GSD 验证工作流。

## 冲突解决

**逆向和确认偏差对抗都寻找失败，但服务不同目的。按顺序运行它们：**

1. **先运行逆向**（头脑风暴）：生成 3 种这可能是错误的方式
2. **再运行确认偏差对抗**（结构化检查）：找到一个部分需求、一个误导测试、一个未覆盖的错误路径

逆向生成列表；确认偏差对抗是验证其中项目的准则。

## 1. 逆向

**针对：** Verifier 确认成功而非发现失败。

不要检查什么是正确的，列出此实现可能错误的 3 种具体方式，尽管测试通过：缺失的边界情况、静默数据丢失、竞态条件、未处理的错误路径。对每种，编写具体检查（grep 模式、以特定输入测试、验证错误处理存在）。此外，检查 SUMMARY.md 中任何记录的 DEVIATION 是否改变了 must-have 的含义或适用性。

## 2. 切斯特顿围栏

**针对：** 将有意的代码标记为死代码或不必要。

在将任何现有代码标记为死代码、冗余或过度复杂之前，确定它为什么以那种方式编写。检查 git blame、注释、测试用例和创建它的 PLAN.md。如果原因不明，标记为"目的未知——建议保留并附 WARNING，不移除"并包含引入它的 commit 的 git blame 哈希。

## 3. 确认偏差对抗

**针对：** 被 SUMMARY.md 的声称引导看到成功的 Verifier。

在初始验证后，做一个反确认检查：（1）找到一个仅部分满足的需求，（2）找到一个通过但实际未测试所述行为的测试，（3）找到一个没有测试覆盖的错误路径。即使总体验证通过，也报告这些。

## 4. 规划谬误校准

**针对：** 接受过度范围的计划为合理（plan-checker）。

对于每个估计为"简单"或"小"的任务，检查：它是否接触超过 2 个文件？它是否需要理解不熟悉的 API？它是否修改共享基础设施？如果以上任何为是，标记为可能低估。拥有 >5 个任务或每个任务接触 >4 个文件的计划是过度范围的。

## 5. 反事实思考

**针对：** 假设每一步都成功且无错误恢复的计划（plan-checker）。

对于每个计划，问："如果 executor 完全按照所写执行此计划，但遇到了常见失败会怎样：依赖版本不匹配、API 返回意外格式、文件已被先前计划修改？"如果计划没有应急路径且 `<action>` 步骤假设每一点都成功，标记为 WARNING："任务 T{n} 无错误恢复路径。"

---

## 何时不思考

在以下情况下跳过结构化推理模型：

- **以前通过的项目的重新验证**——在重新验证模式中，初始检查通过的项目只需要快速回归检查（存在性 + 基本合理），而非完整的逆向 + 确认偏差对抗处理。
- **二进制存在性检查**——如果 must-have 是"文件 X 存在且行数 > N"且文件明显存在且有实质性内容，不要对其运行反事实思考。保留模型用于模糊或依赖接线的 must-have。
- **直接的测试结果**——如果 `<verify>` 命令产生清晰的通过/失败输出（例如测试套件以 0 退出，所有测试通过），接受结果。仅在测试结果模糊或你怀疑测试实际未测试它们声称的内容时才调用模型。
- **INFO 级别问题**——不要应用结构化推理来决定 INFO 级别观察是否实际上是 BLOCKER。INFO 项目定义上就是信息性的，从不触发门。
