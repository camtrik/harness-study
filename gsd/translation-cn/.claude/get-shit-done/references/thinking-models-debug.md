# 思维模型：调试集群

用于 **debugger** agent 的结构化推理模型。在调查中的决策点应用它们，而非持续应用。每个模型针对一个特定的已记录的失败模式。

来源：精选自 [thinking-partner](https://github.com/mattnowdev/thinking-partner) 模型目录（150+ 模型）。选择是因为直接适用于 GSD 调试工作流。

## 冲突解决

**故障树和假设驱动是顺序的：** 先运行故障树（生成可能原因树），再运行假设驱动（系统地测试每个分支）。故障树提供地图；假设驱动提供遍历它的准则。

## 1. 故障树分析

**针对：** 在没有系统映射失败路径的情况下跳到结论。

在测试任何假设之前，构建故障树：以观察到的症状作为根节点，然后在每个级别分支到所有可能的原因（硬件、软件、配置、数据、环境）。使用 AND/OR 门——某些失败需要多个条件（AND），其他的有独立触发（OR）。这棵树成为你的调查路线图。按可能性和可测试性对分支进行优先级排序，但不要仅因为它们看起来不太可能就剪除分支——容易测试但不太可能的原因应该尽早测试。

## 2. 假设驱动调查

**针对：** 随机更改并希望某些东西能奏效——"散弹枪调试"反模式。

对于故障树中的每个假设，遵循严格协议：预测（"如果假设 H 正确，那么测试 T 应产生结果 R"），测试（仅执行一个测试），观察（记录实际结果），结论（匹配 = 支持，失败 = 排除，意外 = 新证据）。绝不要跳过预测步骤——没有预测，你无法区分有意义的结果和噪音。每个测试绝不要更改多于一个变量——如果你改变两样东西而 bug 消失，你不知道哪个更改修复了它。

## 3. 奥卡姆剃刀

**针对：** 在没有排除简单解释的情况下追求复杂解释。

在调查复杂的多组件交互 bug、竞态条件或框架级问题之前，先验证简单解释：变量名拼写错误、文件路径错误、缺少导入、配置值不正确、缓存过期、环境变量错误。这些"无聊"的原因占大多数 bug。仅在简单解释被排除后才升级到复杂假设。如果你当前的假设需要 3+ 个事情同时出错，退一步寻找单点故障。

## 4. 反事实思考

**针对：** 未能通过不问"如果我们只改变这一件事会怎样"来隔离因果关系。

当你有一个关于根因的假设时，构建一个反事实："如果我只改变这一个变量/配置/行，bug 应该消失（或出现）。"执行反事实测试。如果在你针对性的更改后 bug 仍然存在，你的假设是错误的——原因在别处。如果 bug 消失，你有强大的因果证据。这比相关性（"bug 在部署 X 之后出现"）更强大，因为它测试的是机制，而不仅仅是时间线。

## 何时不思考

在以下情况下跳过结构化推理模型：

- **明显的单一原因 bug**——如果错误消息命名了确切的文件、行和原因（例如 `TypeError: Cannot read property 'x' of undefined at foo.js:42`），直接修复。不要为具有堆栈跟踪的空引用构建故障树。
- **复现已知修复**——如果你从先前的调查中已经知道根因或用户告诉了你确切的问题所在，跳过假设驱动调查，直接修复。
- **拼写错误、缺失导入、错误路径**——如果奥卡姆剃刀能立即解决，直接应用修复，不调用完整模型。模型存在是为了简单检查失败时使用，而不是为了阻碍简单检查。
- **阅读错误日志**——阅读和理解错误输出是正常的调试，不是"决策点"。仅当你有多个合理的假设且需要选择优先测试哪个时才调用模型。
