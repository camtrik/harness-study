# 思维模型：规划集群

用于 **planner** 和 **roadmapper** agent 的结构化推理模型。在计划创建中的决策点应用它们，而非持续应用。每个模型针对一个特定的已记录的失败模式。

来源：精选自 [thinking-partner](https://github.com/mattnowdev/thinking-partner) 模型目录（150+ 模型）。选择是因为直接适用于 GSD 规划工作流。

## 冲突解决

事前验尸和约束分析都在不同粒度上分析风险。先运行约束分析（识别最困难的约束），再运行事前验尸（枚举围绕该约束和计划其余部分的失败模式）。

## 1. 事前验尸分析

**针对：** 乐观的计划分解，忽视失败模式。

在最终确定此计划之前，假设它已经失败。列出 3 个最可能的失败原因——缺少依赖、错误分解、低估复杂度——并添加能及早捕获每个失败原因的缓解步骤或验收标准。

## 2. MECE 分解

**针对：** 重叠的任务（合并冲突）或有间隙的任务（缺失需求）。

在需求级别验证此任务分解是 MECE 的：（1）列出阶段目标中的每个需求，（2）确认每个映射到恰好一个任务的 `<done>`，（3）如果两个任务修改同一文件，确认它们修改不同部分或服务于不同需求，（4）标记未被任何任务覆盖的任何需求。

## 3. 约束分析

**针对：** 将最困难的约束推迟到最后任务，导致后期失败。

识别此阶段中单一最困难的约束——如果它不工作，其他一切都无关紧要的那一件事。将该约束安排为任务 1 或 2，而非最后。如果约束涉及外部 API 或不熟悉的库，在主要实现之前添加一个 spike/概念验证任务。

## 4. 可逆性测试

**针对：** 对廉价决策过度分析，对昂贵决策分析不足。

对于此计划中的每个重要决策，分类为可逆（以后可以低成本更改）或不可逆（以后更改需要迁移、破坏性变更或重大重工）。投入与不可逆性成正比的分析时间。对不可逆决策，在计划中记录理由。

## 5. 知识诅咒对抗

**针对：** 压缩指令导致的计划到 executor 的模糊性。

对于每个 `<action>` 步骤，就像你从未见过这个代码库一样重新阅读。每个名词是否无歧义（哪个文件？哪个函数？哪个端点？）？每个动词是否具体（在哪里添加？如何修改？）？如果一个步骤可能被解读为两种方式，重写它。在每个 action 步骤中包含文件路径、函数名和预期行为。

## 6. 基础比率忽视对抗

**针对：** Planner 忽略低信心研究警告。

在最终确定计划之前，阅读 SUMMARY.md 中的所有 `[NEEDS DECISION]` 项目和 LOW 信心建议。对每个：要么（a）创建一个 `checkpoint:decision` 任务来解决它，要么（b）在计划的偏差说明中记录为什么风险是可接受的。被静默接受的 LOW 信心项目成为未记录的技术债务。

## 差距关闭模式：根因检查

**仅在以下情况适用：** Planner 进入差距关闭模式（由 VERIFICATION.md 中的 `gaps_found` 触发）。

在编写修复计划之前，应用单轮"为什么"：为什么会出现这个差距？是计划缺陷（错误的任务）、执行失误（正确的任务、错误的实现）还是改变的假设（环境/依赖变化）？修复计划必须针对根因类别，而不仅仅是症状。

---

## 何时不思考

在以下情况下跳过结构化推理模型：

- **单任务计划**——如果阶段有一个明确需求和一个明显的任务，不要运行事前验尸或 MECE 分析。直接编写任务。
- **研究充分的阶段**——如果 RESEARCH.md 对每个决策都有 HIGH 信心建议且没有 `[NEEDS DECISION]` 项目，跳过基础比率忽视对抗。研究已经解决了不确定性。
- **修订迭代**——当基于检查器反馈修订计划时，专注于修复被标记的问题。不要在每次修订中重新运行完整模型套件——仅应用与特定问题相关的模型。
- **样板计划**——配置更改、版本升级、文档更新。这些没有值得事前验尸分析的失败模式。
