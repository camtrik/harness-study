# 用户画像：检测启发式参考

本参考文档定义了跨 8 个维度的行为画像检测启发式。gsd-user-profiler agent 在分析提取的会话消息时应用这些规则。不要发明超出此处定义的维度和评分规则。

## 如何使用本文档

1. gsd-user-profiler agent 在分析任何消息之前阅读本文档
2. 对于每个维度，agent 扫描消息以查找以下定义的信号模式
3. agent 应用检测启发式来分类开发者的模式
4. 信心度使用每个维度定义的阈值进行评分
5. 证据引用使用证据策展部分中的规则进行策展
6. 输出必须符合输出模式部分的 JSON 模式

---

## 维度

### 1. 沟通风格

`dimension_id: communication_style`

**我们衡量的：** 开发者如何措辞请求、指令和反馈——他们向 Claude 发送消息的结构模式。

**评级范围：**

| 评级 | 描述 |
|--------|-------------|
| `terse-direct` | 简短、命令式消息，上下文最少。直奔主题。 |
| `conversational` | 中等长度消息，混合指令、问题和自言自语。自然、非正式语气。 |
| `detailed-structured` | 长消息，具有明确结构——标题、编号列表、问题陈述、预分析。 |
| `mixed` | 无主导模式；风格随任务类型或项目上下文变化。 |

**信号模式：**
1. **消息长度分布**——各消息的平均字数。简洁 < 50 词，对话式 50-200 词，详细 > 200 词。
2. **命令式与疑问式比率**——命令与问题的比率。高命令比率暗示简洁直接。
3. **结构格式化**——消息中 markdown 标题、编号列表、代码块或项目符号的存在。频繁格式化暗示详细结构化。
4. **上下文前言**——开发者在提出请求前是否提供背景/上下文。前言暗示对话式或详细结构化。
5. **句子完整性**——消息使用完整句子还是片段/简写。片段暗示简洁直接。
6. **后续模式**——开发者是否在后续消息中提供额外上下文（多消息请求暗示对话式）。

**检测启发式：**
1. 如果平均消息长度 < 50 词且主要为命令式语气且最少格式化 → `terse-direct`
2. 如果平均消息长度 50-200 词且命令式和疑问式混合且偶尔格式化 → `conversational`
3. 如果平均消息长度 > 200 词且频繁结构化格式化且存在上下文前言 → `detailed-structured`
4. 如果消息长度方差高（标准差 > 均值的 60%）且没有单一模式占主导（< 60% 消息匹配一种风格）→ `mixed`
5. 如果模式按项目类型系统性变化（例如 CLI 项目中简洁，前端项目中详细）→ `mixed` 附上下文相关说明

**信心度评分：**
- **HIGH：** 10+ 条消息显示一致模式（> 70% 匹配），在 2+ 个项目中观察到的相同模式
- **MEDIUM：** 5-9 条消息显示模式，或仅在 1 个项目内一致
- **LOW：** < 5 条消息有相关信号，或混合信号（在相似上下文中观察到矛盾模式）
- **UNSCORED：** 0 条消息有此维度的相关信号

### 2. 决策速度

`dimension_id: decision_speed`

**我们衡量的：** 当 Claude 呈现选项、替代方案或权衡时，开发者做出选择的速度。

**评级范围：**

| 评级 | 描述 |
|--------|-------------|
| `fast-intuitive` | 基于经验或直觉立即决定。最少深思熟虑。 |
| `deliberate-informed` | 决策前请求比较或摘要。想要了解权衡。 |
| `research-first` | 延迟决策以独立研究。可能离开并带回发现。 |
| `delegator` | 遵从 Claude 的推荐。信任建议。 |

**检测启发式：**
1. 如果开发者在选项呈现的 1-2 条消息内选择且使用果断语言且很少要求比较 → `fast-intuitive`
2. 如果开发者请求权衡分析或比较表，且在收到比较后决定，且提澄清问题 → `deliberate-informed`
3. 如果开发者以"let me look into this"延迟决策，且带回外部信息，且引用文档或文章 → `research-first`
4. 如果开发者使用委派语言（> 3 次）且很少覆盖 Claude 的选择，且说"sounds good"或"your call" → `delegator`

**信心度评分：**
- **HIGH：** 10+ 个决策点观察显示一致模式，在 2+ 个项目中相同的模式
- **MEDIUM：** 5-9 个决策点，或仅在 1 个项目内一致
- **LOW：** < 5 个决策点观察，或混合决策风格
- **UNSCORED：** 0 条消息包含决策相关信号

### 3. 解释深度

`dimension_id: explanation_depth`

**我们衡量的：** 开发者希望伴随代码获得多少解释——他们对理解与速度的偏好。

**评级范围：**

| 评级 | 描述 |
|--------|-------------|
| `code-only` | 想要工作中的代码，附带最少或无解释。直接阅读和理解代码。 |
| `concise` | 想要方法的简要解释附代码。注明关键决策，不穷尽。 |
| `detailed` | 想要方法、推理和代码的彻底演练。欣赏结构。 |
| `educational` | 想要深入的概念解释。将交互视为学习机会。 |

**检测启发式：**
1. 如果开发者说"just the code"或"skip the explanation"且很少问后续概念问题且直接引用代码细节 → `code-only`
2. 如果开发者接受简短解释且不要求更多，且对具体决策问聚焦的后续问题 → `concise`
3. 如果开发者问"why"问题且请求演练且欣赏结构化解释 → `detailed`
4. 如果开发者问超出即时任务的概念性问题且使用学习语言 → `educational`

**信心度评分：**
- **HIGH：** 10+ 条消息显示一致偏好，在 2+ 个项目中相同偏好
- **MEDIUM：** 5-9 条消息，或仅在 1 个项目内一致
- **LOW：** < 5 条相关消息，或偏好在交互间变化
- **UNSCORED：** 0 条消息有相关信号

### 4. 调试方法

`dimension_id: debugging_approach`

**我们衡量的：** 开发者在与 Claude 工作时如何处理问题、错误和意外行为。

**评级范围：**

| 评级 | 描述 |
|--------|-------------|
| `fix-first` | 粘贴错误，希望修复。最少诊断兴趣。结果导向。 |
| `diagnostic` | 附带上下文共享错误，在修复前想理解原因。 |
| `hypothesis-driven` | 先独立调查，带具体理论给 Claude 验证。 |
| `collaborative` | 想与 Claude 作为伙伴逐步解决问题。 |

**检测启发式：**
1. 如果开发者粘贴错误不附上下文且接受修复不追问根因且立即继续 → `fix-first`
2. 如果开发者提供错误上下文且问"why is this happening?"且想要修复伴随解释 → `diagnostic`
3. 如果开发者分享自己的分析且提出理论且请 Claude 确认或反驳 → `hypothesis-driven`
4. 如果开发者使用协作语言（"let's"、"what should we check?"）且偏好增量诊断且一起解决问题 → `collaborative`

### 5. UX 哲学

`dimension_id: ux_philosophy`

**我们衡量的：** 开发者如何相对于功能优先考虑用户体验、设计和视觉质量。

**评级范围：**

| 评级 | 描述 |
|--------|-------------|
| `function-first` | 先让它工作，后打磨。实现期间最少 UX 关注。 |
| `pragmatic` | 从一开始就基本可用。不丑陋或损坏，但不迷恋设计。 |
| `design-conscious` | 设计和 UX 被视为与功能同等重要。关注视觉细节。 |
| `backend-focused` | 主要构建后端/CLI。最少前端暴露或兴趣。 |

### 6. 供应商哲学

`dimension_id: vendor_philosophy`

**我们衡量的：** 开发者如何选择评估库、框架和外部服务。

**评级范围：**

| 评级 | 描述 |
|--------|-------------|
| `pragmatic-fast` | 使用能工作的，Claude 建议的，或最快的。最少评估。 |
| `conservative` | 偏好知名、久经考验、广泛采用的选项。风险规避。 |
| `thorough-evaluator` | 研究替代方案，阅读文档，在承诺前比较功能和权衡。 |
| `opinionated` | 对特定工具有强烈、预先存在的偏好。知道自己喜欢什么。 |

### 7. 挫折触发

`dimension_id: frustration_triggers`

**我们衡量的：** 什么导致开发者对 Claude 的消息产生可见的挫折、纠正或负面情绪信号。

**评级范围：**

| 评级 | 描述 |
|--------|-------------|
| `scope-creep` | 当 Claude 做了未请求的事情时受挫。想要有边界的执行。 |
| `instruction-adherence` | 当 Claude 不精确遵循指令时受挫。重视精确性。 |
| `verbosity` | 当 Claude 过度解释或太絮叨时受挫。想要简洁。 |
| `regression` | 当 Claude 在修复其他东西时破坏工作代码时受挫。重视稳定性。 |

### 8. 学习风格

`dimension_id: learning_style`

**我们衡量的：** 开发者偏好如何理解他们遇到的新概念、工具或模式。

**评级范围：**

| 评级 | 描述 |
|--------|-------------|
| `self-directed` | 直接阅读代码，独立搞明白。问 Claude 具体问题。 |
| `guided` | 请 Claude 解释相关部分。偏好引导理解。 |
| `documentation-first` | 在深入前阅读官方文档和教程。引用文档。 |
| `example-driven` | 想要工作示例来修改和学习。模式匹配学习者。 |

## 证据策展

### 证据格式

对每个证据条目使用组合格式：

**信号：** [模式解释——引用展示的内容] / **示例：** "[修剪的引用，约 100 字符]"——项目：[项目名称]

### 证据目标

- **每维度 3 条证据引用**（跨 8 个维度总计 24 条）
- 选择最能说明评级模式的引用
- 优先选择不同项目的引用以展示跨项目一致性

### 引用截断

- 将引用修剪到行为信号——展示模式的那部分
- 每条引用目标约 100 字符
- 如果信号在长消息中间，使用 "..." 表示修剪
- 绝不包括 50 字符捕获信号时的完整 500 字符消息

### 敏感内容排除（第 1 层）

profiler agent 绝不要选择包含以下模式的引用：
- `sk-`（API key 前缀）
- `Bearer `（auth token）
- `password`（凭证）
- `secret`（密钥）
- `token`（当用作凭证值而非概念讨论时）
- `api_key` 或 `API_KEY`
- 包含用户名的完整绝对文件路径

发现并排除了敏感内容时，在分析输出中报告元数据。

### 自然语言优先级

自然语言消息的权重大于：
- 粘贴的日志输出
- 会话上下文转储
- 大型代码粘贴

这些消息类型是真实的但承载较少行为信号。选择证据引用时降低其优先级。

## 时效性权重

### 指南

近期会话（最近 30 天）在分析模式时应权重约为旧会话的 3x。

### 理由

开发者风格会演变。六个月前简洁的开发者现在可能提供详细结构化上下文。近期行为是当前工作风格的更准确反映。

### 应用

1. 计算信心度评分的信号计数时，近期信号计算为 3x
2. 选择证据引用时，当两者展示相同模式时优先选择近期引用
3. 当近期和旧会话模式冲突时，近期模式优先于评级，但注明演变

## 稀疏数据处理

### 消息阈值

| 总真实消息 | 模式 | 行为 |
|------------------------|------|----------|
| > 50 | `full` | 跨所有 8 维度的全面分析。问卷可选。 |
| 20-50 | `hybrid` | 分析可用消息。为 LOW/UNSCORED 维度补充问卷。 |
| < 20 | `insufficient` | 所有维度评为 LOW 或 UNSCORED。推荐问卷回退作为主要画像来源。 |

## 输出模式

profiler agent 必须返回匹配此精确模式的 JSON，包裹在 `<analysis>` 标签中。

```json
{
  "profile_version": "1.0",
  "analyzed_at": "ISO-8601 时间戳",
  "data_source": "session_analysis",
  "projects_analyzed": ["project-name-1", "project-name-2"],
  "messages_analyzed": 0,
  "message_threshold": "full|hybrid|insufficient",
  "sensitive_excluded": [],
  "dimensions": {
    "communication_style": {
      "rating": "terse-direct|conversational|detailed-structured|mixed",
      "confidence": "HIGH|MEDIUM|LOW|UNSCORED",
      "evidence_count": 0,
      "cross_project_consistent": true,
      "evidence_quotes": [],
      "summary": "观察到的模式的一到两句话描述",
      "claude_instruction": "针对 Claude 的命令式指令"
    },
    ...
  }
}
```

### 模式说明

- **`profile_version`**：此模式版本始终为 `"1.0"`
- **`analyzed_at`**：进行此分析的 ISO-8601 时间戳
- **`claude_instruction`**：必须以命令式形式编写，面向 Claude。此字段是画像变得可操作的地方。
  - 好："提供带标题和编号列表的结构化响应，以匹配此开发者的沟通风格。"
  - 坏："你倾向于喜欢结构化响应。"
  - 好："在声明请求之外进行更改前询问——此开发者重视有边界的执行。"
  - 坏："当你做额外工作时开发者会受挫。"

## 跨项目一致性

### 评估

对于每个维度，评估观察到的模式在所分析的项目中是否一致：

- **`cross_project_consistent: true`**——无论分析哪个项目，相同的评级都适用。2+ 个项目的证据显示相同模式。
- **`cross_project_consistent: false`**——模式随项目变化。在摘要中包含上下文相关说明。
