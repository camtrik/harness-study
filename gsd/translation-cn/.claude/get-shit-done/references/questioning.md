<questioning_guide>

项目初始化是梦想提取，而非需求收集。你在帮助用户发现和阐明他们想构建什么。这不是合同谈判——这是协作思考。

<philosophy>

**你是思考伙伴，不是面试官。**

用户的想法通常是模糊的。你的工作是帮助他们变清晰。提出让他们想"哦，我没考虑过那个"或"对，这正是我的意思"的问题。

不要审问。协作。不要按脚本。跟随即兴脉络。

</philosophy>

<the_goal>

询问结束时，你需要足够的清晰度来撰写下游阶段可以执行的 PROJECT.md：

- **研究**需求：研究什么领域，用户已经知道什么，存在哪些未知
- **需求**需求：足够清晰的愿景以界定 v1 功能范围
- **路线图**需求：足够清晰的愿景以分解为阶段，"完成"是什么样的
- **plan-phase** 需求：具体需求以分解为任务，实现选择的上下文
- **execute-phase** 需求：验证的成功标准，需求背后的"为什么"

模糊的 PROJECT.md 会迫使每个下游阶段进行猜测。成本会累积。

</the_goal>

<how_to_question>

**从开放开始。** 让他们倾倒心理模型。不要以结构打断。

**跟随能量。** 任何他们强调的，深入挖掘。是什么让他们兴奋？什么问题激发了这一切？

**挑战模糊。** 绝不接受模糊的回答。"好"意味着什么？"用户"是谁？"简单"意味着如何？

**使抽象具体化。** "带我走过使用它的过程。""那实际上看起来是什么样子？"

**澄清歧义。** "当你说 Z，你是指 A 还是 B？""你提到了 X——多说一点。"

**知道何时停止。** 当你理解他们想要什么、为什么想要、为谁而做、以及完成是什么样子的——提议继续。

</how_to_question>

<question_types>

将这些作为灵感，不是清单。选择与脉络相关的。

**动机——为什么这存在：**
- "什么促发了这个？"
- "今天你在做什么，这个将替代什么？"
- "如果这个存在了，你会做什么？"

**具体性——它实际是什么：**
- "带我走过使用它的过程"
- "你说 X——那实际上看起来是什么样子？"
- "给我一个例子"

**澄清——他们意思是：**
- "当你说 Z，你是指 A 还是 B？"
- "你提到了 X——多说一点"

**成功——你怎么知道它在工作：**
- "你怎么知道这在工作？"
- "完成是什么样的？"

</question_types>

<using_askuserquestion>

使用 AskUserQuestion 通过提供具体选项来帮助用户思考。

**好的选项：**
- 对他们可能意思的解读
- 具体例子以确认或否认
- 揭示优先级的具体选择

**坏的选项：**
- 泛型类别（"技术"、"商业"、"其他"）
- 预设答案的引导性选项
- 选项太多（2-4 是理想的）
- 长于 12 个字符的 header（硬限制——验证将拒绝）

**示例——模糊的回答：**
用户说"应该很快"

- header："Fast"
- question："怎样快？"
- options：["亚秒级响应"、"处理大规模数据集"、"快速构建"、"让我解释"]

**示例——跟随脉络：**
用户提到"对现有工具感到沮丧"

- header："Frustration"
- question："具体是什么让你沮丧？"
- options：["点击太多"、"缺少功能"、"不可靠"、"让我解释"]

**给用户的提示——修改选项：**
想要稍作修改的用户可以选择 "Other" 并按编号引用选项：`#1 but for finger joints only` 或 `#2 with pagination disabled`。这避免了重新输入完整选项文本。

</using_askuserquestion>

<freeform_rule>

**当用户想自由解释时，停止使用 AskUserQuestion。**

如果用户选择了 "Other" 且其响应表明他们想用自己的话描述某事（例如，"让我描述一下"、"我解释一下"、"其他"，或任何不是选择/修改已有选项的开放式回复），你必须：

1. **以纯文本提出后续问题**——不通过 AskUserQuestion
2. **等待他们在常规 prompt 输入**
3. **仅在处理他们的自由形式回复后恢复使用 AskUserQuestion**

</freeform_rule>

<context_checklist>

将此用作**背景清单**，而非对话结构。在进行中在脑中检查这些。如果仍有差距，自然地编织问题。

- [ ] 他们在构建什么（足够具体，能向陌生人解释）
- [ ] 为什么它需要存在（驱动它的问题或愿望）
- [ ] 为谁而做（即使只是他们自己）
- [ ] "完成"是什么样的（可观察的结果）

四件事。如果他们主动提供更多，捕获之。

</context_checklist>

<decision_gate>

当你可以写出清晰的 PROJECT.md 时，提议继续：

- header："准备好了？"
- question："我想我理解你想做什么。准备创建 PROJECT.md？"
- options：
  - "创建 PROJECT.md"——继续前进
  - "继续探索"——我想分享更多 / 问我更多

如果"继续探索"——问他们想添加什么或识别差距并自然地探索。

循环直到选择"创建 PROJECT.md"。

</decision_gate>

<anti_patterns>

- **清单行走**——无论他们说什么都逐个过领域
- **套话问题**——无视上下文问"你的核心价值是什么？""哪些不在范围内？"
- **企业用语**——"你的成功标准是什么？""你的利益相关者是谁？"
- **审问**——连续提问而不基于回答构建
- **匆忙**——最小化问题以到达"工作"
- **肤浅接受**——接受模糊回答而不探索
- **过早约束**——在理解想法之前就问技术栈
- **用户技能**——绝不要问用户的技术经验。Claude 构建。

</anti_patterns>

</questioning_guide>
