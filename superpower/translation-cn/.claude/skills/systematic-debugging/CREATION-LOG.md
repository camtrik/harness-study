# 创建日志: Systematic Debugging Skill

提取、结构和强化关键技能的参考示例。

## 源材料

从 `~/.claude/CLAUDE.md` 提取调试框架:
- 4 阶段系统化流程（调查 → 模式分析 → 假设 → 实现）
- 核心要求: 始终找到根本原因，永远不要修复症状
- 旨在抵抗时间压力和合理化的规则

## 提取决策

**包含内容:**
- 完整的 4 阶段框架及所有规则
- 反快捷方式（"永远不要修复症状"、"停止并重新分析"）
- 抗压力语言（"即使更快"、"即使我看起来很匆忙"）
- 每个阶段的具体步骤

**排除内容:**
- 项目特定的上下文
- 相同规则的重复变体
- 叙述性解释（浓缩为原则）

## 遵循 skill-creation/SKILL.md 的结构

1. **丰富的 when_to_use** - 包含症状和反模式
2. **类型: technique** - 带有步骤的具体流程
3. **关键词** - "root cause"、"symptom"、"workaround"、"debugging"、"investigation"
4. **流程图** - "修复失败"的决策点 → 重新分析 vs 添加更多修复
5. **逐阶段分解** - 可扫描的检查清单格式
6. **反模式部分** - 不做什么（对这个技能至关重要）

## 强化元素

框架设计用于抵抗压力下的合理化:

### 语言选择
- "始终"/"永远不要"（不是"应该"/"尝试"）
- "即使更快"/"即使我看起来很匆忙"
- "停止并重新分析"（明确的暂停）
- "不要跳过"（捕获实际行为）

### 结构防御
- **需要阶段 1** - 不能跳到实现
- **单一假设规则** - 强制思考，防止霰弹枪式修复
- **明确的失败模式** - "如果第一次修复不起作用"带有强制操作
- **反模式部分** - 精确显示快捷方式的样子

### 冗余
- 概述 + when_to_use + 阶段 1 + 实现规则中的根本原因要求
- "永远不要修复症状"在不同上下文中出现 4 次
- 每个阶段都有明确的"不要跳过"指导

## 测试方法

按照 skills/meta/testing-skills-with-subagents 创建了 4 个验证测试:

### 测试 1: 学术上下文（无压力）
- 简单 bug，无时间压力
- **结果:** 完全遵守，完整调查

### 测试 2: 时间压力 + 明显的快速修复
- 用户"很匆忙"，症状修复看起来很容易
- **结果:** 抵制快捷方式，遵循完整流程，找到真正的根本原因

### 测试 3: 复杂系统 + 不确定性
- 多层失败，不清楚是否能找到根本原因
- **结果:** 系统化调查，追踪所有层，找到源头

### 测试 4: 第一次修复失败
- 假设不起作用，想要添加更多修复的诱惑
- **结果:** 停止，重新分析，形成新假设（无霰弹枪式）

**所有测试通过。** 未发现合理化。

## 关键洞察

**最重要的强化:** 反模式部分显示了在当下感觉合理的精确快捷方式。当 Claude 想"我只添加这个快速修复"时，看到那个精确模式被列为错误会产生认知摩擦。

## 使用示例

遇到 bug 时:
1. 加载技能: skills/debugging/systematic-debugging
2. 阅读概述（10 秒）- 提醒要求
3. 遵循阶段 1 检查清单 - 强制调查
4. 如果想要跳过 - 看到反模式，停止
5. 完成所有阶段 - 找到根本原因

**时间投入:** 5-10 分钟
**节省时间:** 数小时的症状打地鼠游戏
