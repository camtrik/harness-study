# 系统化调试

## 概述

随意的修复浪费时间并制造新的缺陷。快速补丁掩盖了深层问题。

**核心原则：** 在尝试修复之前，始终找到根本原因。修复症状就是失败。

**违反本流程的字面规定就是在违反调试的精神。**

## 铁律

```
不先完成根本原因调查，不得提出修复方案
```

如果你还没有完成第 1 阶段，就不能提出修复方案。

## 何时使用

适用于任何技术问题：
- 测试失败
- 生产环境的缺陷
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**特别在以下情况下使用：**
- 时间紧迫时（紧急情况让猜测变得诱人）
- "就一个快速修复"看起来很明显时
- 你已经尝试了多次修复
- 之前的修复无效
- 你还没有完全理解问题

**以下情况下不要跳过：**
- 问题看起来很简单（简单缺陷也有根本原因）
- 你很着急（匆忙必然导致返工）
- 管理者要求"现在就修"（系统化比反复折腾更快）

## 四个阶段

必须完成每个阶段后才能进入下一个阶段。

### 第 1 阶段：根本原因调查

**在尝试任何修复之前：**

1. **仔细阅读错误信息**
   - 不要略过错误或警告
   - 它们通常包含了确切的解决方案
   - 完整阅读堆栈追踪
   - 注意行号、文件路径、错误码

2. **稳定复现**
   - 能可靠触发吗？
   - 确切步骤是什么？
   - 每次都发生吗？
   - 如果不能复现 → 收集更多数据，不要猜测

3. **检查最近的变更**
   - 什么变更可能导致这个问题？
   - Git diff、最近的提交
   - 新的依赖项、配置变更
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统有多个组件时（CI → 构建 → 签名，API → 服务 → 数据库）：**

   **在提出修复方案之前，添加诊断检测：**
   ```
   对于每个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置的传播
     - 检查每一层的状态

   运行一次以收集证据，显示它在何处中断
   然后分析证据以识别故障组件
   然后调查该特定组件
   ```

   **示例（多层系统）：**
   ```bash
   # 第 1 层：工作流
   echo "=== 工作流中可用的密钥: ==="
   echo "IDENTITY: ${IDENTITY:+已设置}${IDENTITY:-未设置}"

   # 第 2 层：构建脚本
   echo "=== 构建脚本中的环境变量: ==="
   env | grep IDENTITY || echo "IDENTITY 不在环境中"

   # 第 3 层：签名脚本
   echo "=== Keychain 状态: ==="
   security list-keychains
   security find-identity -v

   # 第 4 层：实际签名
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这揭示了：** 哪一层失败了（密钥 → 工作流 ✓，工作流 → 构建 ✗）

5. **追踪数据流**

   **当错误在调用栈深处时：**

   参见本目录中的 `root-cause-tracing.md` 了解完整的反向追踪技术。

   **快速版本：**
   - 无效值从哪里产生？
   - 什么用无效值调用了这里？
   - 继续向上追踪直到找到源头
   - 在源头修复，而非在症状处

### 第 2 阶段：模式分析

**在修复之前找到模式：**

1. **找到正常工作的示例**
   - 在同一代码库中找到类似的可工作代码
   - 哪些运行正常的代码与出问题的代码类似？

2. **对比参考实现**
   - 如果正在实施某个模式，完整阅读参考实现
   - 不要略读——阅读每一行
   - 在应用之前完全理解该模式

3. **识别差异**
   - 正常工作的和出问题的之间有什么差异？
   - 列出每一个差异，无论多小
   - 不要假设"那个不可能有影响"

4. **理解依赖关系**
   - 这个组件需要哪些其他组件？
   - 需要什么设置、配置、环境？
   - 它做了哪些假设？

### 第 3 阶段：假设与测试

**科学方法：**

1. **形成单一假设**
   - 清晰地陈述："我认为 X 是根本原因，因为 Y"
   - 写下来
   - 要具体，不要模糊

2. **最小化测试**
   - 做最小的可能变更来测试假设
   - 每次只改变一个变量
   - 不要同时修复多个东西

3. **验证后再继续**
   - 成功了吗？是 → 第 4 阶段
   - 没成功？形成新的假设
   - 不要在上面叠加更多修复

4. **当你不确定时**
   - 直接说"我不理解 X"
   - 不要假装知道
   - 寻求帮助
   - 继续研究

### 第 4 阶段：实施

**修复根本原因，而非症状：**

1. **创建失败的测试用例**
   - 最简单的复现方式
   - 尽可能使用自动化测试
   - 如果没有框架，使用一次性测试脚本
   - 修复前必须有测试
   - 使用 `superpowers:test-driven-development` skill 编写正确的失败测试

2. **实施单一修复**
   - 解决已识别的根本原因
   - 一次只做一个变更
   - 不要"既然来了就顺便"改进
   - 不要捆绑重构

3. **验证修复**
   - 测试现在通过了吗？
   - 没有其他测试被破坏？
   - 问题确实解决了吗？

4. **如果修复无效**
   - 停止
   - 计数：你已经尝试了多少次修复？
   - 如果 < 3：返回第 1 阶段，用新信息重新分析
   - **如果 ≥ 3：停止并质疑架构（见下面第 5 步）**
   - 在没有架构讨论之前不要尝试第 4 次修复

5. **如果 3 次以上修复失败：质疑架构**

   **表明架构问题的模式：**
   - 每次修复都在不同地方揭示出新的共享状态/耦合/问题
   - 修复需要"大规模重构"才能实施
   - 每次修复都在其他地方产生新症状

   **停止并质疑根本问题：**
   - 这个模式从根本上讲合理吗？
   - 我们是否"仅凭惯性在坚持"？
   - 我们是应该重构架构，还是继续修复症状？

   **在尝试更多修复之前和你的搭档讨论**

   这不是假设失败——这是架构错误。

## 红旗——停止并遵循流程

如果你发现自己正在想：
- "先快速修复，后面再调查"
- "就试试改 X 看看能不能用"
- "加多个变更，跑测试"
- "跳过测试，我手动验证"
- "很可能是 X，让我修一下"
- "我没完全理解，但这个可能有效"
- "模式说 X，但我会按不同方式适配"
- "以下是主要问题：[列出修复方案，但没有调查]"
- 在追踪数据流之前就提出解决方案
- **"再试一次修复"（已经尝试了 2 次以上时）**
- **每次修复都在不同地方揭示新问题**

**以上所有情况都意味着：停止。返回第 1 阶段。**

**如果 3 次以上修复失败：** 质疑架构（参见第 4.5 阶段）

## 人类搭档发出的"你做错了"信号

**注意以下纠正信号：**
- "那不是没发生吗？"——你在没有验证的情况下做出了假设
- "它会告诉我们……？"——你应该添加证据收集
- "别猜了"——你在没有理解的情况下提出修复方案
- "深层思考一下"——质疑根本问题，而不只是症状
- "我们卡住了？"（沮丧）——你的方法不奏效

**当你看到这些信号时：** 停止。返回第 1 阶段。

## 常见的合理化借口

| 借口 | 现实 |
|------|------|
| "问题很简单，不需要流程" | 简单问题也有根本原因。对于简单缺陷，流程也很快。 |
| "紧急情况，没时间走流程" | 系统化调试比反复猜测和检查更快。 |
| "先试试这个，然后再调查" | 第一次修复定下基调。从一开始就做对。 |
| "确认修复有效后再写测试" | 未经测试的修复不会稳固。先测试以证明。 |
| "一次做多个修复节省时间" | 无法隔离哪个有效。还会导致新缺陷。 |
| "参考太长，我按模式改编一下" | 部分理解必然导致缺陷。完整阅读它。 |
| "我看到问题了，让我修" | 看到症状 ≠ 理解根本原因。 |
| "再试一次修复"（已失败 2 次以上） | 3 次以上失败 = 架构问题。质疑模式，不要再修复了。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|------|----------|----------|
| **1. 根本原因** | 阅读错误信息、复现、检查变更、收集证据 | 理解"发生了什么"和"为什么" |
| **2. 模式** | 找到正常工作的示例、对比差异 | 识别差异 |
| **3. 假设** | 形成理论、最小化测试 | 确认或形成新假设 |
| **4. 实施** | 创建测试、修复、验证 | 缺陷已解决、测试通过 |

## 当流程揭示出"没有根本原因"时

如果系统化调查揭示问题确实是由环境、时序或外部因素导致的：

1. 你已经完成了流程
2. 记录你调查了什么
3. 实施适当的处理（重试、超时、错误信息）
4. 添加监控/日志供未来调查

**但是：** 95% 的"没有根本原因"案例都是调查不完整。

这些技术是系统化调试的一部分，可在本目录中找到：

## 实际效果

来自调试会话：
- 系统化方法：15-30 分钟修复
- 随意修复方法：2-3 小时的反复折腾
- 首次修复成功率：95% vs 40%
- 引入的新缺陷：接近零 vs 常见
