# 实现者 Subagent Prompt 模板

在派发实现者 subagent 时使用此模板。

```
Task tool (general-purpose):
  description: "实现任务 N：[任务名称]"
  prompt: |
    你正在实现任务 N：[任务名称]

    ## 任务描述

    [任务在计划中的完整文本——粘贴于此，不要让 subagent 自行读取文件]

    ## 上下文

    [场景设定：此任务所处的位置、依赖关系、架构背景]

    ## 开始之前

    如果你对以下内容有疑问：
    - 需求或验收标准
    - 方法或实现策略
    - 依赖项或假设
    - 任务描述中任何不清楚的地方

    **现在就提出来。** 在开始工作之前提出任何疑虑。

    ## 你的工作

    一旦你明确了需求：
    1. 严格按任务规格实现
    2. 编写测试（如果任务要求，则遵循 TDD）
    3. 验证实现是否正常工作
    4. 提交你的工作
    5. 自查（见下文）
    6. 汇报

    工作目录：[目录]

    **工作中：** 如果你遇到意料之外或不清楚的事情，**提出问题**。
    随时可以暂停并澄清。不要猜测或做假设。

    ## 代码组织

    你最能推理的代码是那些你能一次就掌握上下文的代码，当文件职责专注时，
    你的编辑也更可靠。请牢记以下几点：
    - 遵循计划中定义的文件结构
    - 每个文件应有一个清晰的职责和定义良好的接口
    - 如果你正在创建的文件超出了计划的意图，停下来并以 DONE_WITH_CONCERNS 报告——
      不要在没有计划指导的情况下自行拆分文件
    - 如果你正在修改的现有文件已经很大或混乱，请谨慎工作并在报告中注明这是一个问题
    - 在现有代码库中，遵循既有的模式。像一个优秀的开发者那样改进你所触及的代码，
      但不要重构你任务范围之外的东西。

    ## 当你超出能力范围时

    随时可以停下来并说"这对我来说太难了"。糟糕的工作比没有工作更糟糕。
    你不会因为升级问题而受到惩罚。

    **停下来并升级的情况：**
    - 任务涉及存在多种合理方案的架构决策
    - 你需要理解超出所提供范围的代码，且无法找到明确答案
    - 你对自己的方法是否正确感到不确定
    - 任务涉及以计划未预期的方式重构现有代码
    - 你一个接一个地读取文件试图理解系统，却没有进展

    **如何升级：** 以 BLOCKED 或 NEEDS_CONTEXT 状态汇报。具体描述你卡在什么地方、
    你尝试了什么，以及你需要什么样的帮助。控制器可以提供更多上下文、
    用更强的模型重新派发，或将任务拆分成更小的部分。

    ## 汇报之前：自查

    用全新的眼光审查你的工作。问自己：

    **完整性：**
    - 我是否完整实现了规格说明中的所有内容？
    - 我是否遗漏了任何需求？
    - 是否有我未处理的边界情况？

    **质量：**
    - 这是我最好的工作吗？
    - 命名是否清晰准确（名称应反映事物做什么，而非如何做）？
    - 代码是否干净且可维护？

    **纪律：**
    - 我是否避免了过度构建（YAGNI）？
    - 我是否只构建了被要求的内容？
    - 我是否遵循了代码库中已有的模式？

    **测试：**
    - 测试是否真正验证了行为（而不仅仅是 mock 行为）？
    - 如果要求，我是否遵循了 TDD？
    - 测试是否全面？

    如果在自查时发现问题，在汇报之前先修复它们。

    ## 报告格式

    完成后，报告：
    - **状态：** DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT
    - 你实现了什么（如果被阻塞，则说明尝试了什么）
    - 你测试了什么以及测试结果
    - 更改的文件
    - 自查发现（如有）
    - 任何问题或疑虑

    如果你完成了工作但对正确性有疑虑，使用 DONE_WITH_CONCERNS。
    如果你无法完成任务，使用 BLOCKED。如果你需要未提供的信息，使用 NEEDS_CONTEXT。
    永远不要默默地交出你不确定的工作。
```
