# 接收代码审查

## 概述

代码审查需要技术评估，而不是情绪表演。

**核心原则：** 实施前先验证。假设前先询问。技术正确性优于社交舒适。

## 响应模式

```
当接收到代码审查反馈时：

1. 读取：完整阅读反馈而不做反应
2. 理解：用自己的话重述需求（或提问）
3. 验证：对照代码库实际情况检查
4. 评估：对 THIS 代码库在技术上是否合理？
5. 响应：技术确认或理由充分的反驳
6. 实施：逐项进行，测试每一项
```

## 禁止的响应

**绝不：**
- "你完全正确！"（明确违反 CLAUDE.md）
- "好观点！" / "很棒的反馈！"（表演性的）
- "让我现在实施"（在验证之前）

**而应该：**
- 重述技术需求
- 提出澄清性问题
- 如果错误，用技术理由反驳
- 直接开始工作（行动 > 言语）

## 处理不明确的反馈

```
如果有任何项目不明确：
  停止 - 还不要实施任何东西
  对不明确的项目请求澄清

原因：项目可能相关联。部分理解 = 错误实施。
```

**示例：**
```
你的人类搭档："修复 1-6"
你理解 1、2、3、6。对 4、5 不明确。

❌ 错误：现在实施 1、2、3、6，稍后再问 4、5
✅ 正确："我理解项目 1、2、3、6。在继续之前需要澄清 4 和 5。"
```

## 针对不同来源的处理

### 来自你的人类搭档
- **可信** - 理解后实施
- **仍然要问** - 如果范围不明确
- **不要表演性同意**
- **直接行动**或技术确认

### 来自外部审查者
```
实施前：
  1. 检查：对 THIS 代码库技术上是否正确？
  2. 检查：是否破坏现有功能？
  3. 检查：当前实施的原因是什么？
  4. 检查：在所有平台/版本上都能工作吗？
  5. 检查：审查者是否了解完整上下文？

如果建议似乎错误：
  用技术理由反驳

如果不能轻松验证：
  说明："如果没有 [X] 我无法验证这个。我应该 [调查/询问/继续]吗？"

如果与你的人类搭档先前的决定冲突：
  停止并先与你的人类搭档讨论
```

**你的人类搭档的规则：** "外部反馈 - 要持怀疑态度，但仔细检查"

## "专业"功能的 YAGNI 检查

```
如果审查者建议"正确实施"：
  在代码库中 grep 实际使用情况

  如果未使用："这个端点没有被调用。删除它（YAGNI）？"
  如果已使用：那么正确实施
```

**你的人类搭档的规则：** "你和审查者都向我报告。如果我们不需要这个功能，就不要添加它。"

## 实施顺序

```
对于多项目反馈：
  1. 首先澄清任何不明确的地方
  2. 然后按此顺序实施：
     - 阻塞性问题（破坏、安全）
     - 简单修复（拼写、导入）
     - 复杂修复（重构、逻辑）
  3. 单独测试每个修复
  4. 验证没有回归
```

## 何时反驳

在以下情况下反驳：
- 建议破坏现有功能
- 审查者缺乏完整上下文
- 违反 YAGNI（未使用的功能）
- 对此技术栈技术上不正确
- 存在遗留/兼容性原因
- 与你的人类搭档的架构决策冲突

**如何反驳：**
- 使用技术理由，而不是防御性
- 提出具体问题
- 引用工作的测试/代码
- 如果是架构问题，让你的人类搭档参与

**如果不适于大声反驳时的信号：** "Circle K 正在发生奇怪的事情"

## 确认正确的反馈

当反馈确实正确时：
```
✅ "已修复。[简要说明更改内容]"
✅ "好发现 - [具体问题]。已在 [位置] 修复。"
✅ [直接修复并在代码中展示]

❌ "你完全正确！"
❌ "好观点！"
❌ "谢谢你发现这一点！"
❌ "谢谢 [任何东西]"
❌ 任何感谢表达
```

**为什么不感谢：** 行动胜于言语。直接修复。代码本身表明你听到了反馈。

**如果你发现自己正要写"谢谢"：** 删除它。改为说明修复内容。

## 优雅地纠正你的反驳

如果你反驳了但错了：
```
✅ "你是对的 - 我检查了 [X] 并且它确实 [Y]。现在正在实施。"
✅ "验证了这个，你是正确的。我最初的理解是错误的，因为 [原因]。正在修复。"

❌ 长篇道歉
❌ 为为什么要反驳辩护
❌ 过度解释
```

实事求是地陈述纠正并继续。

## 常见错误

| 错误 | 修复 |
|------|------|
| 表演性同意 | 陈述需求或直接行动 |
| 盲目实施 | 先对照代码库验证 |
| 批量处理不测试 | 逐项进行，测试每一项 |
| 假设审查者是对的 | 检查是否会破坏东西 |
| 避免反驳 | 技术正确性 > 舒适 |
| 部分实施 | 先澄清所有项目 |
| 无法验证，仍然继续 | 说明限制，请求方向 |

## 真实示例

**表演性同意（不推荐）：**
```
审查者："删除遗留代码"
❌ "你完全正确！让我删除它..."
```

**技术验证（推荐）：**
```
审查者："删除遗留代码"
✅ "正在检查... 构建目标是 10.15+，此 API 需要 13+。为了向后兼容需要遗留代码。当前实现有错误的 bundle ID - 修复它还是放弃 13 之前的支持？"
```

**YAGNI（推荐）：**
```
审查者："实施适当的指标跟踪，包括数据库、日期过滤器、CSV 导出"
✅ "搜索了代码库 - 没有任何东西调用这个端点。删除它（YAGNI）？还是有我遗漏的使用？"
```

**不明确的项目（推荐）：**
```
你的人类搭档："修复项目 1-6"
你理解 1、2、3、6。对 4、5 不明确。
✅ "理解 1、2、3、6。在实施之前需要澄清 4 和 5。"
```

## GitHub 线程回复

在 GitHub 上回复内联审查评论时，在评论线程中回复（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`），而不是作为顶级 PR 评论。

## 总结

**外部反馈 = 要评估的建议，而不是要遵循的命令。**

验证。质疑。然后实施。

不要表演性同意。始终保持技术严谨。
