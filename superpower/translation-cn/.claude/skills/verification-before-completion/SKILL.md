# 完成前验证

## 概述

在未经验证的情况下声称工作完成是不诚实，而非高效。

**核心原则：** 先有证据再下声明，始终如此。

**违反此规则的文字，就是违反此规则的精神。**

## 铁律

```
没有新鲜的验证证据，就不能声称完成
```

如果你没有在当前消息中运行验证命令，你就不能声称它通过了。

## 门控函数

```
在声称任何状态或表达满意之前：

1. 确认：哪个命令可以证明这个声明？
2. 运行：执行完整的命令（新鲜的、完整的）
3. 读取：完整输出，检查退出码，统计失败数
4. 验证：输出是否证实了声明？
   - 如果否：用证据陈述实际状态
   - 如果是：附带证据陈述声明
5. 只有在此之后：做出声明

跳过任何一步 = 欺骗，而不是验证
```

## 常见错误

| 声明 | 需要 | 不充分 |
|-------|----------|----------------|
| 测试通过 | 测试命令输出：0 个失败 | 之前的运行、"应该通过" |
| 代码检查干净 | 代码检查输出：0 个错误 | 部分检查、推测 |
| 编译成功 | 编译命令：exit 0 | 代码检查通过、日志看起来不错 |
| Bug 已修复 | 测试原始症状：通过 | 代码改了、假定已修复 |
| 回归测试有效 | 红-绿循环已验证 | 测试通过一次 |
| Agent 已完成 | VCS diff 显示更改 | Agent 报告"成功" |
| 需求已满足 | 逐行清单检查 | 测试通过 |

## 危险信号 - 停下来

- 使用"应该"、"可能"、"似乎"
- 在验证之前表达满意（"太好了！"、"完美！"、"搞定了！"等）
- 即将在未验证的情况下提交/推送/创建 PR
- 信任 agent 的成功报告
- 依赖部分验证
- 想着"就这一次"
- 累了想让工作结束
- **任何未运行验证就暗示成功的措辞**

## 借口预防

| 借口 | 现实 |
|--------|---------|
| "现在应该能工作了" | 运行验证 |
| "我有信心" | 信心 ≠ 证据 |
| "就这一次" | 没有例外 |
| "代码检查通过了" | 代码检查 ≠ 编译器 |
| "Agent 说成功了" | 独立验证 |
| "我累了" | 疲惫 ≠ 借口 |
| "部分检查足够了" | 部分证明不了任何事 |
| "换种说法规则就不适用了" | 精神高于文字 |

## 关键模式

**测试：**
```
✅ [运行测试命令] [看到：34/34 通过] "所有测试通过"
❌ "现在应该能通过" / "看起来正确"
```

**回归测试（TDD 红-绿）：**
```
✅ 写 → 运行（通过）→ 回退修复 → 运行（必须失败）→ 恢复 → 运行（通过）
❌ "我已经写了回归测试"（未做红-绿验证）
```

**编译：**
```
✅ [运行编译] [看到：exit 0] "编译通过"
❌ "代码检查通过了"（代码检查不检查编译）
```

**需求：**
```
✅ 重新阅读计划 → 创建清单 → 验证每一项 → 报告差距或完成
❌ "测试通过，阶段完成"
```

**Agent 委派：**
```
✅ Agent 报告成功 → 检查 VCS diff → 验证更改 → 报告实际状态
❌ 信任 agent 报告
```

## 为什么这很重要

来自 24 条失败记忆：
- 你的人类搭档说"我不相信你"——信任破裂
- 未定义的函数被发布——会崩溃
- 缺失的需求被发布——功能不完整
- 时间浪费在虚假完成 → 重定向 → 重做
- 违反："诚实是核心价值观。如果你撒谎，你将被替换。"

## 何时应用

**始终在以下情况之前：**
- 任何形式的成功/完成声明
- 任何形式的满意表达
- 任何关于工作状态的正面陈述
- 提交、创建 PR、任务完成
- 进入下一个任务
- 委派给 agent

**规则适用于：**
- 精确措辞
- 释义和同义词
- 成功的暗示
- 任何暗示完成/正确的沟通

## 底线

**验证没有捷径。**

运行命令。读取输出。然后才声明结果。

这是不可协商的。
